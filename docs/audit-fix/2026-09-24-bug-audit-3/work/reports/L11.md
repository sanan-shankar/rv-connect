- Confidence: certain (27 run logs, the CLI's own help text, the object sizes and the rows are each observed). What would change my mind: nothing short of a green media job.
- Where:

In every one the `dump` job succeeds and the `media` job fails at "Copy new photos to the private bucket". Every failed copy is the same error, `An error occurred (NotImplemented) when calling the GetObjectTagging operation: GetObjectTagging not implemented`: 1 object on 2026-08-29, then 110-113 a night from 2026-09-01, 111 last night (and 1,955 smaller objects copied fine the same night). Then three alarms failed together: the run is red every night (so it has become the background, 27 failure e-mails that read like the last one), the metric built to surface it independently has 403'd since it was written (T7b-01), and the security board's C4 row, which `npm run check` prints on every run, greps the YAML and says the media backup exists.

- Severity: Medium (no member sees it; it is the privacy contract and the purpose of two security fixes. The owner is the UK controller of record and the page is the document a regulator reads)
- Confidence: certain on the mechanism and the counts; the legal weight of backups under erasure is the owner's call
- Where:

### L11-03 — A mail Resend has accepted is sent a second time two minutes later whenever the one database write that records the acceptance fails: the code parks the row for "the stale-claim sweep to decide", and the sweep can only requeue it (a reset's second mail then burns the first one's link)
- Severity: Low (a duplicate mail, and for a password reset a dead first link with "or you did not do this" copy; no data loss. Rises with pool pressure, i.e. exactly on a launch-day signup burst, which is O-03/T5-17's condition)
- Confidence: certain on the mechanism (every line below read); likely on the trigger occurring at launch (it needs one failed `updateMany` in the instant after an accept; the dev log already shows pool-connect timeouts on single-member page views, findings.md 02:25 BST).   - `src/lib/email-queue.ts:762-765` — the sweep that "decides": `prisma.outboundEmail.updateMany({ where: { status: "sending", claimedAt: { lt: new Date(Date.now() - STALE_CLAIM_MS) } }, data: { status: "queued", claimedAt: null } })` — unconditional requeue, no look at whether a send was accepted; `src/lib/mail-policy.ts:313` (`STALE_CLAIM_MS = 2 * 60_000`); `:328-335` (`drainHasWork` counts exactly this row as work, so the very next authenticated page view runs the pass that requeues it)

- Taxonomy: 6i (a retry after a failure that actually committed at the provider; the queue's claim/reclaim cycle) · 6k (DB slow mid-request) · L9 (a comment that states the opposite of what the sweep does) · 6a (error path continues into an invalid state)
- Expected: the catch's own promise — no second send; "sent" means Resend accepted it exactly once.
- Actual: Resend accepts the message (the member's inbox has it). The `writeIfStillClaimed` updateMany throws: a 5-second pool-connect timeout (`prisma.ts` `connectionTimeoutMillis: 5000`), a dropped pooled connection, the 20-second `query_timeout`. The row stays `sending`.
