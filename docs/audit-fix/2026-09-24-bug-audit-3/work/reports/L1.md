# L1 — races-mutations (lens)
Agent: L1 · Started: 2026-09-24 · Model: claude-fable-5-1
Charter: For every mutation in the app — the 22 server-action files and every writing API route —
answer one question: which of the three server-action race classes apply (double-invocation before
the pending state disables the control; read-modify-write without a transaction or atomic
increment; out-of-order completion of rapid successive actions) and what ACTUALLY guards it: a
`@@unique` with a P2002 handler, an atomic `increment`/`updateMany` precondition, a `$transaction`
with the right isolation, or nothing. Build the mutation × invariant × guard table first, then for
every "nothing" construct the interleaving and say what the member sees. Sweep every `@@unique` in
`schema.prisma` and match it to the rule it protects; list every "only one per X" rule with NO
unique. Check every `$transaction` for network calls inside it, length vs the 5s default timeout,
isolation level, P2034 retry, partial-write handling. Check every `updateMany`-as-CAS for the
count=0 branch. Check every toggle for delete-first+P2002 or in-flight guards. Check double-submit
on every form. Check out-of-order completion on every rapid-fire client action.

## The table — mutation × rows × invariant × guard

Legend for the Guard column: **U+P2002** = a `@@unique` with a handler for the violation ·
**CAS** = conditional `updateMany` whose count=0 branch is handled · **TX** = `$transaction` ·
**DF** = delete-first toggle (deleteMany then create, P2002 = other tap won) · **WIN** = 10s
twin-window dedupe (check-then-insert; catches retries and second tabs, NOT two requests in the
same instant) · **IDEM** = the write is naturally idempotent (setting a flag to the value it
already has) · **MONO** = monotonic conditional update · **NONE** = no server-side guard at all.
Race classes: (1) double-invocation → duplicate rows · (2) read-modify-write → lost update ·
(3) out-of-order completion → older result clobbers newer.

## Findings

### L1-01 — Two partial refunds on one gift delivered together lose one of them: the recovery bar and the member's ledger over-count
- Severity: Medium
- Confidence: likely (mechanism certain; the scenario needs two DISTINCT reversal events for the same order to be processed inside the same ~10ms window — a Razorpay retry burst after a 5xx, two "Resend" presses in the dashboard, or a refund and a dispute landing together)
- Where: `src/app/api/razorpay/webhook/route.ts:178-188` (the read), `:379-385` (`foldReversal` fed from that read), `:391-402` (the write); `src/lib/contribution-state.ts:126-144` (`foldReversal`)
- Taxonomy: 6c(2) read-modify-write · 6i webhooks duplicate/out-of-order · 6d check-then-write
- Expected: the schema (`Contribution.refundedAmount`, `reversalIds`) promises that "a re-delivered refund.processed would [not] subtract the same paise twice" and that every money sum reads `amount MINUS refundedAmount`; C-087's fix ledger promises partial refunds accumulate.
- Actual: two different reversal ids arriving concurrently both pass the `NOT reversalIds has` guard, both compute an ABSOLUTE `refundedAmount` from the row as read at :178, and the second write overwrites the first. The row then carries `reversalIds: [r1, r2]` (so neither can ever be re-applied) but `refundedAmount` = only one of them. Every money surface — the /support recovery bar, "Given, all time", the admin tiles, the supporter's own perk ledger — over-counts by the lost refund, permanently, with an audit line for each reversal that says the right paise.
- Why: the write is
  ```
  const folded = foldReversal({ amount: contribution.amount, refundedAmount: contribution.refundedAmount, ... paise });
  const moved = await prisma.contribution.updateMany({
    where: { id: contribution.id, status: { notIn: [...REVERSED_STATUSES] }, NOT: { reversalIds: { has: reversalId } } },
    data: { status: folded.status, refundedAmount: folded.refundedAmount, reversalIds: { push: reversalId } },
  });
  ```
  `refundedAmount` is written as `Math.min(amount, refundedAmount_read + paise)` — a value, not an increment — and the WHERE carries no condition on `refundedAmount`. Interleaving: A reads {refundedAmount: 0}, B reads {refundedAmount: 0}; A writes 10000 (r1); B's UPDATE waits on A's row lock, re-evaluates its WHERE (status still paid, r2 not in the array) and writes 20000 (r2). Final: 20000, reversalIds [r1, r2]; truth 30000. The dispute-won branch (:312-323) is safe only because its WHERE pins `status: "disputed"`, which the first winner changes.
- Proof: argue-only against the live database (it holds 22 contributions, 0 with a partial refund, no reversed rows). A unit test can prove it without Razorpay: call `POST` twice concurrently with two signed `refund.processed` bodies for one order carrying different `refund.entity.id`s against a test row, then read `refundedAmount`. Alternatively pin the shape: a `-rule.test.mjs` asserting the reversal `updateMany`'s `where` names `refundedAmount`.
- Fix direction: make the fold atomic. Either (a) CAS on the value read — add `refundedAmount: contribution.refundedAmount` (and `status: contribution.status`) to the WHERE and, on `count === 0`, re-read the row and re-run the fold once (the `has` guard still stops a true re-delivery); or (b) write `refundedAmount: { increment: paise }` and flip the status in a second conditional statement `updateMany({ where: { id, refundedAmount: { gte: amount } }, data: { status: to } })` — but then `foldReversal`'s clamp to `amount` has to move into SQL (`LEAST`) or be accepted as a bounded overshoot. (a) is the smaller change and keeps `foldReversal` pure.
- Gate: a route-level test with two concurrent distinct reversals on one row (needs a test DB or a mocked `prisma`), plus a source pin that the reversal write's `where` includes `refundedAmount`.
- Known-related: C-084/C-085/C-087/C-151 fixed the single-event ordering cases; none of them considered two DIFFERENT reversals in flight at once.

### L1-02 — A question removed as answering opens leaves an Edition with nothing to answer, which the C-021 guard cannot see
- Severity: Low (Medium consequence — the B-062 reminder loop and an empty Edition published to the whole group — at a very low probability)
- Confidence: certain on the mechanism; possible on anyone ever hitting it (the window is one Keeper's remove landing within the few ms between its status read and its delete while the open commits — two Keepers, or one Keeper on two tabs, or any member's page view at the exact deadline)
- Where: `src/app/(main)/catchups/actions.ts:1223-1246` (remove: status read at :1233-1240, unconditional `delete` at :1242); the guard it defeats: `:1283-1292` (openAnswering counts prompts INSIDE its tx) and `src/lib/catchups.ts:286-303` (the clock counts prompts, then CASes on status at :159-163)
- Taxonomy: 6c(2) TOCTOU · 6i two surfaces mutating the same row
- Expected: the comment on openAnswering: "Counted INSIDE the transaction, against the same rows advanceEdition counts, so the removal cannot land between the check and the open. There is no way back out of `answering`." And curatePrompt: "Questions can only be curated while the window is open."
- Actual: the count protects the OPEN against a removal that committed before it. It cannot protect against a removal whose status check ran before the open and whose `delete` runs after: `loadKeeperEdition` reads `collecting`, the open's transaction commits (`answering`, everyone notified "Answers are open"), then `prisma.catchupPrompt.delete({ where: { id } })` removes the last question. Result: an `answering` Edition with zero prompts — nobody can write (submitEntry needs a prompt), the daily reminder nags every member for the whole window, the close finds 0 entries and auto-extends once (three more days of nudges), then publishes an empty Edition and tells the group it is "ready to read".
- Why: the delete carries no precondition:
  ```
  if (edition.status !== "collecting") { return { error: "Questions can only be curated while the window is open." }; }
  await prisma.catchupPrompt.delete({ where: { id: promptId } });
  ```
  whereas every other Edition write in this file re-checks status in the statement that writes (submitPrompt :1079, submitEntry :1861, every CAS). The reorder branch has the same shape (:1209-1217) but is harmless past the open.
- Proof: argue-only live. A `node --test` on the action with a mocked client is the honest proof; a source pin is the practical one.
- Fix direction: `deleteMany({ where: { id: promptId, edition: { status: "collecting" } } })` and answer `count === 0` with "This Edition already moved on." (the sentence openAnswering already uses). Doing the same on the reorder branch's updates costs nothing.
- Gate: extend `catchup-lifecycle.test.mjs` (which already pins the `pausedHint` contract for these callers) to assert the remove branch's delete is conditional on `collecting`.
- Known-related: C-021 (openAnswering's empty-Edition guard) — this is its mirror image on the other writer; B-062 is the loop it resurrects.

### L1-03 — The two last Keepers leaving in the same instant leave a Catch-up nobody can tend
- Severity: Low
- Confidence: possible (argue-only; needs both role-holders of a creator-less Catch-up to press Leave/Remove within one transaction's span, ~50ms)
- Where: `src/app/(main)/catchups/actions.ts:2623-2637` (leaveCatchup's tx), `:2549-2555` (removeCatchupMember's tx); `src/lib/group-succession.ts:66-85` (`promoteGroupSuccessor`: `findMany` snapshot at :71-74, `updateMany` at :80-83); `src/lib/account-purge.ts:46-83` (the purge's copy, same shape, inside RepeatableRead)
- Taxonomy: 6c(2) read-modify-write without serialisation · 6i Keeper vs Keeper
- Expected: C-023's fix promise — "Hand the hat on first, if this is the last head wearing it ... A no-op whenever somebody else still holds the powers."
- Actual: K1's transaction reads the members (K1 keeper, K2 keeper, M1) → "somebody else holds it" → null → deletes K1. K2's transaction, started before K1 committed, reads the same snapshot (READ COMMITTED sees only committed rows; K1's delete is not yet committed) → "K1 still holds it" → null → deletes K2. Both commit. M1 is alone with role "member"; `createdById` is null (the case C-023 exists for); `setCatchupKeeper` needs a Keeper to call it; nothing heals it until an account purge happens to run `promoteOrphanedGroups` for one of them. The clock keeps running an Edition nobody can curate, publish early, extend, pause or end.
- Why: `promoteGroupSuccessor` decides from a snapshot and its only write is `updateMany where { groupId, userId: successor }`, which is the right shape for the purge's concern (the successor vanishing) and the wrong one for this: neither transaction touches a row the other reads, so READ COMMITTED lets both proceed.
- Proof: argue-only. Live (read-only, 2026-09-24): of the non-batch Catch-ups, 1 has two role-holders and 1 has one; 0 are currently Keeperless.
- Fix direction: after the `deleteMany` inside the same tx, re-count `groupMember.count({ where: { groupId, role: { in: ["admin","keeper"] } } })` plus `catchup.createdById`; if zero, promote the longest-standing remaining member THEN — a count after the delete under READ COMMITTED still cannot see the other tx's uncommitted delete, so the honest fix is `isolationLevel: "Serializable"` with the P2034 → "try again" handling `refuseSelfOrLastAdmin` already carries (`src/lib/admin.ts:134-173`), or a `SELECT … FOR UPDATE` on the group row (raw) to serialise leavers per group.
- Gate: `group-succession.test.mjs` cannot see this (it is pure); pin that `leaveCatchup`/`removeCatchupMember`'s `$transaction` passes an isolation level, the way `unattended-rule.test.mjs` pins `maxDuration`.
- Known-related: C-023 (Keeperless Catch-up) — the sequential case is fixed; this is the concurrent case.

### L1-04 — The account purge runs RepeatableRead with no P2034 retry, so a heart on the member's post mid-purge fails the purge until tomorrow
- Severity: Low (a transient, self-reporting failure: the nightly sweep answers 502 and GitHub Actions goes red; an admin sees "Could not delete this user. Check the server log." and has to press again)
- Confidence: certain for the direct-update half (Postgres: an UPDATE in a REPEATABLE READ transaction on a row a concurrent transaction updated after the snapshot fails with 40001); likely for the cascade half (`ri_triggers.c` runs `ON DELETE CASCADE` with `detectNewRows` and a crosscheck snapshot under transaction-snapshot isolation, and the executor raises `could not serialize access due to concurrent update` on a child row it cannot see)
- Where: `src/lib/account-purge.ts:345-397` (the tx; options at :382-396 — `timeout: 30_000, isolationLevel: "RepeatableRead"`, no retry), `:400-409` (the catch: `PurgeCancelled` only, everything else → "Could not delete the account."), `:288-301` (`clearCoversPointingAtThisMember` updates OTHER members' rows), `:366-374` (the cascade delete); `src/lib/retention.ts:294-304` (`errors.push("purge:<id>")`), `src/app/api/retention/sweep/route.ts:68` (502 on any error), `src/app/(main)/admin/people/actions.ts:532-535`
- Taxonomy: 6d interactive transaction isolation / P2034 retry · 6i crons partial failure · 6c(2)
- Expected: C-076's fix ledger: "Under RepeatableRead the whole transaction reads one snapshot and a conflicting concurrent write aborts it instead, which is a retry rather than a leak." Nothing retries.
- Actual: any of these committing inside the purge's window (up to 30s for a long-standing member; the transaction runs six collect reads, the tombstone pass, the covers `updateMany`, one `catchup.update` per uploaded picture, then the cascade over ~25 tables) aborts it with P2034: another member liking, commenting on or hearting the member's post/answer/photo (a new child row for the cascade); a bell row minted for the member; any profile edit or the 15-minute `lastSeenAt` stamp on ANY member whose `coverPhoto` is one of the purged member's photographs (`clearCoversPointingAtThisMember` updates those rows); the member's own sign-in cancelling the request (which should read as `PurgeCancelled` and instead reads as a failure). The sweep then reports the night as failed for a race that resolves itself, and the admin's delete button gives a generic failure.
- Why:
  ```
  const outcome = await prisma.$transaction(async (tx) => { ... }, { timeout: 30_000, maxWait: 5_000, isolationLevel: "RepeatableRead" });
  ...
  } catch (err) {
    if (err instanceof PurgeCancelled) { ... return { ok: false, cancelled: true, ... }; }
    console.error("purgeUserAccount failed:", err);
    return { ok: false, error: "Could not delete the account." };
  }
  ```
  Prisma's own guidance for RepeatableRead/Serializable transactions is to catch P2034 and retry; `refuseSelfOrLastAdmin` (`src/lib/admin.ts:167-169`) does exactly that for its Serializable transaction and this file does not.
- Proof: argue-only against the shared database (a rolled-back experiment is the honest proof and is off-limits to this audit). The orchestrator can prove the direct-update half with two sessions on a throwaway account: BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT from "User"; in session 2 UPDATE the throwaway's row; back in session 1 `UPDATE "User" SET "coverPhoto"=NULL WHERE id=<throwaway>` → 40001. Live exposure: 1 account currently carries `deletionRequestedAt`; `PendingImagePurge` is empty.
- Fix direction: wrap the `$transaction` in a small loop — on `err.code === "P2034"` re-run up to three times (the collect runs again from a fresh snapshot, which is exactly what the isolation level is for); if it still fails, return a distinct `{ ok: false, retryable: true }` so the sweep counts it under a new `accountsDeferred` rather than `errors`, and the admin sees "Somebody was interacting with this account's content just now; try again." Keep `PurgeCancelled` as it is.
- Gate: a source pin in `unattended-rule.test.mjs` (or a sibling) that `purgeUserAccount` names `P2034`; a unit test of the retry wrapper with a fake client that throws P2034 once.
- Known-related: C-076 chose the isolation level; C-075 made the delete conditional. Neither added the retry the first one's own ledger line assumes.
