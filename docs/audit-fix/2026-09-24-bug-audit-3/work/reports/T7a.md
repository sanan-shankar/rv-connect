# T7a — admin-purge-retention
Agent: T7a · Started: 2026-09-24 · Model: Fable 5.1 (claude-fable-5-1)
Charter: The admin surface and its two destructive back-rooms. Every page under `src/app/(main)/admin/**` and the admin layout; the people, reports, review and mail actions; every component in `src/components/admin/*` except analytics/ and messages/; the admin libraries (`admin.ts`, `admin-people*.ts`, `admin-review.ts`, `admin-content*.ts`, `admin-worklist-query.ts`, `admin-note.ts`, `audit.ts`, `prisma-errors.ts`); the account purge (`account-purge.ts`) and the retention sweep (`retention.ts` + `/api/retention/sweep` + `retention.yml`); the image-purge drain; the roster importer; the lab's admin gate and `LabRoomState` writes; and the AuditLog, Report, AdminThread, AdminMessage and PendingImagePurge schema blocks. Nothing was signed in, nothing was written, the sweep and the purge were never run. ## Findings

### T7a-01 — Deleting a member (admin delete, the 60-day sweep, or a merge) silently destroys every report they ever FILED, pending ones included, while the privacy policy promises the opposite
- Severity: Medium
- Confidence: certain (the delete is explicit in the code; the promise is on the public page). What would change my mind: nothing about the mechanism; the severity drops to Low only if the owner decides a reporter's reports are theirs to take with them, and then the privacy page must change.
- Where: `src/lib/account-purge.ts:354-362`; `prisma/schema.prisma:829` (`reporter User @relation("ReportsFiled", fields: [reporterId], references: [id])` — required, no `onDelete`, so Postgres RESTRICT); `src/app/(main)/admin/people/actions.ts:405-407` (the merge drops them the same way); `src/app/(policies)/privacy/page.tsx:168-171`; `src/lib/retention.ts:32-34`.
- Taxonomy: 6d (onDelete cascades vs app-level cleanup), 6h identity states (report whose reporter is purged), 6i (delete vs the member's own request), L9 (a promise the code does not keep).
- Expected: the privacy page: *"A few things outlive deletion, deliberately: contribution records..., **reports that were part of moderation decisions**, and a one-line audit record"*. `retention.ts:32-34` keeps reports three years because *"a pattern of being reported is the thing it exists to show"*. `docs/spec/admin.md` §9.3: *"you cannot see that the same person has been reported five times. That is the one fact a moderation queue exists to surface."*
- Actual: `purgeUserAccount` runs `await tx.report.deleteMany({ where: { reporterId: userId } });` before the row delete — every report the member filed, pending or settled, against anyone, is gone. The merge does the same for the duplicate (`prisma.report.deleteMany({ where: { reporterId: sourceId } })`) rather than moving them. Reports filed AGAINST the member cascade too (`schema.prisma:831`), which is defensible; the FILED ones are other people's moderation history. In the member's terms: a member reports someone for harassment, then (weeks later) asks to delete their own account, or an admin merges their duplicate away, or an admin deletes them — and the pending report against the harasser leaves the queue with no trace, the "N reports in all" pattern count drops, and the settled history of that harasser shrinks. The only survivor is the `report.user` audit row, which no page groups by target.
- Why: the comment at `account-purge.ts:354-358` explains the mechanism honestly ("a member who has EVER filed a report cannot be deleted until those rows are cleared") — the design chose delete over detach because the FK is required. The schema already has the right instrument for exactly this next door: `Comment.authorId` (`schema.prisma:780`, `String?` + `SetNull`, argued at 746-755) and `AdminMessage.authorId` (`:953`). `Report.reporterId` never got it. Evidence that reports do vanish on this database: `SELECT count(*) FROM "AdminThread" WHERE kind='report' AND "reportId" IS NULL` = 1 while every one of the 4 live reports has no thread — a report row has already been deleted out from under its conversation (by a post delete, a purge or a merge; see T7a-02 for the post half).
- Proof: read-only, the orphan thread above. Live proof needs the throwaway account: file a report from it against Jerry, then `adminDeleteUser(throwaway)` — the Reports queue loses the row. Do not prove with a real member.
- Fix direction: make `Report.reporterId` nullable with `onDelete: SetNull` (a dated file in `prisma/migrations-manual/`, `ALTER TABLE "Report" ALTER COLUMN "reporterId" DROP NOT NULL` + drop/recreate the FK with SET NULL), remove the `report.deleteMany` from the purge and the merge, render "filed by a member who has since left" where `reporter` is null (`report-list.tsx:69-74`, `admin-worklist-query.ts:182-183`), and have the merge MOVE the duplicate's filed reports (dropping only the rows that would collide on `@@unique([reporterId, reportedUserId])`, the same shed-then-move shape it already uses for memberships). Mind the partial unique `Report_open_post_per_reporter_key` on (reporterId, postId): a moved report can collide there too.
- Gate: `src/lib/cascade-rule.test.mjs` — assert the Report edge from `reporter` is SetNull, not Default/Restrict; `src/lib/purge-rule.test.mjs` — assert `purgeUserAccount` contains no `report.deleteMany`.
- Known-related: none in the baseline. Audit-2 H8 made the purge clear the RESTRICT rows so the delete could succeed; this is the cost of how H8 was closed.

### T7a-02 — When the author of a reported post deletes it, the report vanishes from the queue with no decision, and the reporter is never answered
- Severity: Medium
- Confidence: certain on mechanism (FK cascade); likely on consequence (the reporter's thread survives, so an admin who reads Messages carefully may still act; nothing tells them the report is gone).
- Where: `prisma/schema.prisma:830` (`post Post? @relation(fields: [postId], references: [id], onDelete: Cascade)`); `src/app/(main)/feed/actions.ts:447-466` (`deletePost`) and the helper it calls (`deletePostWithImages`, ~66-102) touch notifications and images but never reports; `src/lib/admin-threads-server.ts:119-124` (`noteOnReportThread` is only reached from `settleReport`, which needs the row); `prisma/schema.prisma:931` (`AdminThread.reportId` SetNull, "keeps the conversation alive if the reported post (and with it the report) is deleted").
- Taxonomy: 6d cascades, 6h identity (report whose post is gone), 6k (the evidence disappears mid-review).
- Expected: `report-action.ts` promises the reporter, in the thread's first line, *"An admin will look into it."* The Reports page (`reports/page.tsx:42-53`) exists so that a settled report is never "permanently out of reach". The schema comment on `AdminThread.reportId` knows the report dies with the post and keeps the conversation — but the conversation is never closed.
- Actual: a member reports a post; before an admin opens `/admin/reports`, the author deletes the post (their own hard delete, `deletePost`). Postgres cascades the Report row away. The Reports queue and the Overview worklist no longer show it; the rail's Reports count drops; `priorReports` never counted it. What remains is an `AdminThread` of kind `"report"` with `reportId: null`, still `adminUnread: true` (set at filing, `report-action.ts:54`), whose only content is the app's own "You reported a post by X, saying: ..." line — under Messages, not Reports, with no "Talk to" link from any report row and no closing note ever written. The reporter waits for a verdict that cannot come. The evidence (the words) is gone with the post; the report's `reason` (which may quote them) is gone with the row.
- Why: `Report.postId` is `Cascade` (`:830`); the reason is that a report about a post has "nothing left to hang under". But the thread comment (`:922-923`) already treats the report as something that outlives the post. The two halves of one design disagree, and neither side writes the closing note. Read-only evidence: the 1 report-kind thread with a NULL `reportId` (see T7a-01).
- Proof: read-only — the orphan thread. Live: throwaway account reports one of Jerry's posts; Jerry (dev-login as Jerry only) deletes the post; `/admin/reports` shows nothing, `/admin/messages` shows the thread.
- Fix direction: two acceptable shapes. (a) Keep the row: `postId` SetNull + store `postExcerpt`/`postAuthorId` on the Report at filing time so the queue can still say what it was about; the settle actions already tolerate a null post. (b) Keep the cascade but make `deletePostWithImages` settle the report first: `report.updateMany({ where: { postId, status: "pending" }, data: { status: "dismissed" } })` plus `noteOnReportThread(..., "The post you reported has since been removed by its author.")`, inside the same transaction. (b) is smaller; (a) keeps the history the spec says the page exists for.
- Gate: a test in the feed/report area asserting that `deletePostWithImages` either notes the report thread or that the Report edge to Post is SetNull; `gate-coverage`-style shape assertion.
- Known-related: C-054 (bell rows) is the sibling class, fixed for notifications only.

### T7a-03 — No admin surface shows that a member has asked to delete their account, so an admin can verify, promote, or merge a duplicate INTO an account that the sweep will erase
- Severity: Medium
- Confidence: certain (grep: zero reads of `deletionRequestedAt` under `src/app/(main)/admin`, `src/components/admin`, `src/lib/admin*.ts`, `admin-profile-tools.tsx`).
- Where: `src/app/(main)/admin/people/[id]/page.tsx:33-60` (the select has no `deletionRequestedAt`); `src/lib/admin-people.ts:159-173` (`PersonRow` has no such field, and no "leaving" state in `STATE_OPTIONS:38-43`); `src/lib/admin-worklist-query.ts:84-166` (no queue for it); `src/app/(main)/admin/people/actions.ts:348-356` (`adminMergeUsers` reads the target as `{ id, photoUrl }` only — no check of `deletionRequestedAt` or `isBlocked`); `src/components/admin/people/person-detail.tsx:176-274` (Standing shows email, member, joined; nothing about leaving).
- Taxonomy: 6h identity states (deletion-requested user on every admin surface), 6i (two surfaces mutating the same row: the member's request vs the admin's merge/verify).
- Expected: `docs/spec/admin.md` §9.4: the detail page holds "identity and standing". `schema.prisma:117-123`: while `deletionRequestedAt` is set "the account is held out of the directory and search the same way a blocked one is" — the People list shows Blocked as a chip (`people-list.tsx:223`); the equally hidden "leaving" state shows nothing.
- Actual, in the owner's terms: (a) a member writes "I asked to delete my account three weeks ago, please just do it" — the admin opens their page and sees a normal verified member, no date, no request; the only trace is an `account.delete_request` line on `/admin/audit`, 100 rows deep and unfiltered. (b) The directory hides them; the admin's People list shows them as ordinary and cannot filter for them. (c) The sharp edge: an admin finds a duplicate signup and merges it INTO the member's older account, not knowing that older account has a deletion request maturing — every post, photograph, Catch-up answer and contribution moved by the merge is erased by the sweep on the due night (the merge does not clear `deletionRequestedAt`, and the sweep needs no confirmation). The merge dialog (`person-detail.tsx:403-444`) asks only for a pasted id and the duplicate's name.
- Why: the column was added with the self-deletion feature (audit M35) and wired into the directory and search, never into the panel that was built afterwards from a plan that predates it. Nothing in the merge or verify actions consults it.
- Proof: read-only — the grep above; today `deletion_requested = 0`, so nothing is live-affected. Live: throwaway requests deletion (its own settings), then open `/admin/people/<id>`: nothing shows.
- Fix direction: select `deletionRequestedAt` into `PersonRow` and `DetailPerson`; a "Leaving <valley date>" chip in `statusChip` (ahead of Admin, after Blocked) and a Standing fact; a `leaving` value in `STATE_OPTIONS`/`peopleWhere`; `adminMergeUsers` refuses (or requires a second confirmation for) a target with `deletionRequestedAt` set or `isBlocked: true`; optionally a worklist line "due for erasure this week".
- Gate: a shape test that the person page's select and `adminMergeUsers`' target read both name `deletionRequestedAt`.
- Known-related: none.

### T7a-04 — After a purge, other members' bells still point at the erased member's letters (404) and posts, for up to 30 days; the explicit-delete path was fixed (C-054), the purge path was not
- Severity: Medium (a member-visible 404 from their own bell; the class audit 2 rated High for hides/deletes)
- Confidence: certain on mechanism; today's data shows 0 dangling links because the 4 purges predate the letters feature's notifications.
- Where: `src/lib/account-purge.ts:344-397` (the transaction never touches `Notification`; the member's posts go by FK cascade, `schema.prisma:716`, so no app code runs for them); `src/lib/post-notifications.ts:81-91` (`clearPostNotifications` exists); `src/app/(main)/feed/actions.ts:447-466` + helper (`deletePost` clears them "inside"); `src/app/(main)/feed/actions.ts:495` (`adminRemovePost` clears them).
- Taxonomy: 6d (cascade vs app-level cleanup), 6h identity (deleted user referenced by live notifications), C-054's class.
- Expected: `post-notifications.ts:61-70`: "Take down the bell rows that point at a post that is no longer readable... Notifications are kept until the 30-day sweep, so the window is a month (C-054)."
- Actual: `purgeUserAccount` deletes the account; Postgres cascades the posts; every "X replied to your comment" / "X liked your letter" row in OTHER members' bells whose `link` is `/letters/<id>` now opens the hoopoe 404, and `/feed#<id>` rows land on the feed with nothing to scroll to — until the 30-day sweep. Separately, those rows' `message` text still carries the erased member's name for the same month, after a purge whose stated meaning is "erase COMPLETELY" (`account-purge.ts:10`).
- Why: the purge collects image URLs and tombstones comments in app code precisely because cascades cannot do it; notifications were left to the cascade, which only removes the purged member's OWN bell (`schema.prisma:893`).

Live: throwaway writes a letter, Jerry comments on it (a bell row for the throwaway... reversed: Jerry writes the letter? No — the throwaway must be the AUTHOR of the letter and Jerry the commenter, then a like from the throwaway on Jerry's comment mints a bell row in Jerry's bell pointing at `/letters/<throwaway's letter>`); delete the throwaway; Jerry's bell 404s.
- Fix direction: inside the purge transaction, before `user.deleteMany`, read the member's post ids and kinds and run `tx.notification.deleteMany({ where: { link: { in: posts.map(postNotificationLink) } } })`; consider also `message: { contains: name }` for the name residue (a product call — the sweep gets them in 30 days anyway).
- Gate: `purge-rule.test.mjs` shape assertion that `purgeUserAccount` names `postNotificationLink`/`notification.deleteMany` before `user.deleteMany`.
- Known-related: C-054 (fixed for hide/delete/letters); this is the same hole on the path nobody listed.

### T7a-05 — An admin's "Delete for good" runs a 30-second transaction plus up to 500 sequential R2 deletes inside a page-hosted server action with no `maxDuration`; if the platform cuts it, the account is gone but no `admin.delete` audit line is ever written and the admin is told "That did not go through"
- Severity: Medium if the project runs on the legacy Hobby 10s default; Low if Fluid compute (300s) is on. I could not read the Vercel dashboard.
- Confidence: possible on the trigger (plan/default unknown — the brief says "Hobby: 10s default", `sweep/route.ts:37` says "300 seconds is the Hobby plan's ceiling", which is the Fluid number; both cannot be true of this project); certain on the ordering defect once it triggers.
- Where: `src/app/(main)/admin/people/actions.ts:532-548` (purge, THEN audit); `src/lib/account-purge.ts:411` (`drainPendingImagePurges(urls)` after the commit, sequential, `limit = 500` at `:430`); no `export const maxDuration` on `src/app/(main)/admin/people/[id]/page.tsx` or `src/app/(main)/profile/[id]/page.tsx` (the two pages hosting the action; `grep maxDuration src/app` lists neither); `src/lib/unattended-rule.test.mjs:165-167` records that "a Server Action inherits its timeout from the page that hosts it".
- Taxonomy: 6f (function duration; nothing after the response without `after()`), 6g (delete-path ordering), 6a (errors continuing into an invalid state).
- Expected: `account-purge.ts:319-320`: "The count returned is objects actually gone... the audit entry the CALLER writes quotes it". `docs/SECURITY.md` and `/admin/audit` promise the deletion is on the record.
- Actual: a member with, say, 150 Collection photographs (3 objects each = 450 keys, well inside the 1,960-photo archive's shape) is deleted from the panel. The transaction commits (rows gone, worklist written — good). The function then issues ~450 `DeleteObject` calls one at a time. Under a 10s ceiling it is killed mid-loop: the rest stay in `PendingImagePurge` (durable, the sweep finishes them — good), but `writeAudit({ action: "admin.delete" ... })` at `:537` never runs, `revalidatePath` never runs, and the client's `callAction` turns the dropped connection into "That did not go through. Check your connection and try again." — for a deletion that did go through. The admin clicks again: "Could not find..." / 404. Under Fluid's 300s none of this triggers; the audit gap is then only a crash-window defect.
- Why: the audit write sits after the slowest, least-necessary step; nothing scopes the in-request drain to what a request can afford.
- Proof: argue-only (destructive). Read-only check of exposure: `SELECT "uploaderId", count(*) FROM "Photo" GROUP BY 1 ORDER BY 2 DESC LIMIT 5` shows how many keys a single delete would drain. The plan question goes to L8 (leads below).
- Fix direction: write the audit line immediately after the transaction (quote the queued count, and let the sweep's own line report what R2 later accepted), then drain; move the drain into `after()` (with the `try { after } catch { void fn() }` shape TRAPS demands for non-request callers), or cap the in-request drain at ~50 and leave the rest to the sweep; export `maxDuration` on both hosting pages.
- Gate: `unattended-rule.test.mjs` — add the two hosting pages to the maxDuration list; `purge-rule.test.mjs` — assert the `admin.delete` audit write precedes `drainPendingImagePurges` in the call chain (or that the drain is inside `after`).
- Known-related: C-079 (maxDuration on the cron routes and image routes); this is the same finding on the one destructive server action.

- Known-related: routed from L1 (leads-routed.md, first T7a row) — confirmed and widened: the orchestrator's list missed the admin's OWN `adminUpdatePerson` as a trigger and the password-reset path.

### T7a-07 — A merge, and the purge's own succession, hand a Catch-up's Keeper hat over as group role "admin", which the Keeper's revoke can never take back (routed lead, confirmed and widened)
- Severity: Medium-Low (an un-revocable Keeper on a real Catch-up, created by the app itself; the revoke reports success while changing nothing)
- Confidence: certain.
- Where: `src/app/(main)/admin/people/actions.ts:383-389` (merge: `data: { role: "admin" }`); `src/lib/account-purge.ts:76-79` (`promoteOrphanedGroups`: `data: { role: "admin" }`); versus `src/lib/group-succession.ts:80-83` (the leave path writes `"keeper"`); `src/app/(main)/catchups/actions.ts:2727-2745` (revoke is `where: { ..., role: "keeper" }`; on `count === 0` with the member still present the action falls through and returns success — "this control is not the place to take away" the group admin role, and since Groups were removed there is no place at all); `src/lib/catchups-core.ts:445` ("Read both; only ever write `keeper`").
- Taxonomy: 6a (contract drift between three writers of one column), 6h identity, L9 (comment vs code).
- Expected: `catchups-core.ts:431-455` and the revoke's own comment: Keeper power is granted by writing `"keeper"` so it can be revoked by matching `"keeper"`.
- Actual: (a) merge: the duplicate held Keeper (or the legacy creator-row "admin") in a Catch-up the survivor was already a plain member of → the survivor's row becomes `"admin"`. (b) purge: the last Keeper of a group is erased → `chooseGroupSuccessor` picks the longest-standing member and writes `"admin"`. In both, the new Keeper shows in the Catch-up as a Keeper (`isEffectiveKeeper` reads both roles), and when the real Keeper later presses "take the hat back", the `updateMany` matches 0 rows, `stillHere > 0`, and the action returns success — the hat stays on. The only remedy is SQL by hand. (The `deletePost` moderation power the comment fears no longer exists — `Post.groupId` left the schema on 2026-09-07 — so the extra power is nil; the un-revocability is the whole consequence.)
- Why: three writers, two vocabularies, and a revoke scoped to one of them (C-025 narrowed the revoke without checking who else writes the column).
- Proof: read-only — `SELECT role, count(*) FROM "GroupMember" GROUP BY 1` shows how many "admin" rows exist today (creators' own rows are expected). Live: argue-only (needs a merge or a purge).
- Fix direction: both the merge's carry-over and `promoteOrphanedGroups` write `"keeper"`, matching `promoteGroupSuccessor`; and the revoke's silent fall-through should return an honest refusal ("they hold the group's own admin role") rather than success — or, simpler now that Groups are gone, the revoke should match `role: { in: ["keeper", "admin"] }` except for the creator's row.
- Gate: `group-succession.test.mjs` — assert both succession writers use the same role string; a shape test that no file writes `role: "admin"` onto GroupMember except Catch-up creation.
- Known-related: routed from L1 (second T7a row) — confirmed; the purge's own writer at `account-purge.ts:78` is the widening.

### T7a-08 — The "flagged" member state is dead: nothing in the app can write it, yet a worklist queue, a rail count, a People filter arm, a chip, a Standing line and two comments are built on it
