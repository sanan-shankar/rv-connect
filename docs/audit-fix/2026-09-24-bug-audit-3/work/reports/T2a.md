### T2a-01 — Correcting a batch year leaves the member inside the wrong batch's Catch-up for ever, with no way out (7 live cases)
- Severity: High
- Confidence: certain (7 members in the live database are in two batch groups today; the code has no path that removes a stale batch membership)
- Where:
  - `src/lib/batch-catchups.ts:83-118` (`joinBatchGroup`: find-or-create the group, `upsert` the membership, `ensureBatchCatchup`) — adds, never removes
  - `src/lib/batch-catchups.ts:218-250` (`healBatchGroupMemberships`: "every alumnus with a batch year is in their batch group") — the raw query only finds members MISSING from the group of their current year; nothing looks for members PRESENT in a group whose year is not theirs
  - `src/components/profile/profile-actions.ts:228-240` (a member changes `batchYear`/`yearLeft`; `prisma.user.update` only) and `src/app/(main)/admin/people/actions.ts:114-174` (an admin corrects `batchYear`; `User` row only) — neither touches `GroupMember`
  - `src/components/auth/actions.ts:199-205` (signup is the only caller of `joinBatchGroup` besides the heal)
  - `src/app/(main)/catchups/actions.ts:2613-2615` (`leaveCatchup` refuses a batch: `BATCH_LEAVE_REFUSAL`) and `:2409-2413` (`loadKeeperScope` refuses `removeCatchupMember` on a batch) — so the mis-filed member cannot leave and nobody can remove them
  - `src/lib/catchups-core.ts:533-534` (`BATCH_LEAVE_REFUSAL`: "This is your batch's Catch-up, so there is nobody to leave it to.")
- Taxonomy: 6h identity states (batch-keyed surfaces) · 6i (two surfaces mutating the same fact: profile vs group) · 6j (a false member counts toward `BATCH_CATCHUP_FLOOR`)
- Expected: spec §2.1 "the membership is the batch"; `healBatchGroupMemberships` docblock: "every alumnus with a batch year is in their batch group". One batch group per member, the one for the year on their row.
- Actual: a member who signed up with the wrong year (or whose year an admin corrected) is added to the new batch's group by signup/the heal and stays in the old one. They see two batch Catch-ups on `/catchups`, appear in the wrong batch's People dialog, receive that batch's questions-open / answers-open / daily reminders, can ask and answer in it, and when they try to leave are told "This is your batch's Catch-up, so there is nobody to leave it to". A Keeper cannot remove them (batch: `BATCH_CATCHUP_REFUSAL`). Archiving is the only relief and it keeps the notifications coming (archiving is filing, spec §5).
- Why: `joinBatchGroup` is `upsert`-only and the heal's query is `NOT EXISTS (member row in the group whose batchYear = u.batchYear)` — it can only ADD. No code path anywhere deletes a `GroupMember` row from a batch group (`leaveCatchup` and `removeCatchupMember` both refuse batch groups by design; the purge cascades the whole user). Live data, `SELECT u.name, u."batchYear", string_agg(g."batchYear") ... HAVING count(*) > 1 OR bool_or(g."batchYear" <> u."batchYear")` returns 7 rows: Rukmini Rau (row 2024; groups 2016, 2024), Chinmay Tumbe (2002; 2022, 2002 — both joined 2026-09-11, i.e. corrected the same day), Harshita Tibrewal (2026; 2024, 2026), Arnav Gupta (2021; 2019, 2021), Gayathri Narayanan (1988; 1986, 1988), Soumya Saraf (2022; 2025, 2022), Rose B (2022; 2023, 2022). That is 7 of 213 (3.3%) after four weeks of signups; Batch of 2022's Catch-up (39 members) therefore carries a 2002 alumnus, and Batch of 2019's (20) carries a 2021 one. The floor is also affected: `ensureBatchCatchup` counts `_count.members` (`batch-catchups.ts:158`), so a stale member can be the tenth that mints a batch Catch-up.
- Proof: read-only — run the query above (it is in this report's SQL trail); open `/admin/catchups/<Batch of 2022 id>` and see the roster count include the 2002 alumnus. Throwaway account: sign up Jerry-like with year X, correct the year to Y on the profile, wait for the tick (or open `/admin/catchups`), see two batch memberships.
- Fix direction: make batch membership follow the row. Either (a) on every `batchYear` write (profile action, admin action, signup correction) move the membership: delete the `GroupMember` row from any batch group whose year is not the new one, then `joinBatchGroup`; and (b) extend the heal with the mirror query ("a member row in a batch group whose year differs from the user's") so the tick repairs the seven and any future drift. Clear that member's pref row and Catch-up notifications for the old batch (the same `clearCatchupNotifications` leave does). Decide with the owner whether a member's answers in the wrong batch's published Editions stay (leaving keeps them by his rule). Do not touch people Catch-ups. Run the repair on both databases.
- Gate: `batch-catchups.test.mjs` gains a test that the heal has both directions (pin the presence of the mirror query and that every `batchYear` writer calls the mover); a one-off `run-sql.mjs --inline` count of the query above must return 0 after the repair.
- Known-related: dedup C-020 (rejoin via invite never cleared the bin) is the same shape — membership state that only moves one way — but on people Catch-ups; C-046 (`import-roster.mjs`) is roster matching, not group membership. Not in the baseline.

### T2a-03 — A Keeper can enrol the whole community: the 100-person cap is per call, `addCatchupMembers` is unmetered, and nobody added is told
- Severity: Medium
- Confidence: certain (mechanism); the abuse needs a verified member acting badly, the scale cost needs a big roster
- Where:
  - `src/app/(main)/catchups/actions.ts:2443-2449` (`addCatchupMembers`: `z.array(...).min(1).max(MAX_CATCHUP_PEOPLE)` on the CALL; no read of the existing roster size; no `rateLimit`)
  - `src/lib/catchup-caps.ts:17-27` ("the cap is the reach limit as much as the roster limit") — it is neither past the first call
  - `src/app/(main)/catchups/actions.ts:2436-2437` (the gate comment: "Enrols other people and notifies each of them. Reaching real members waits for a confirmed address") — nothing in the function notifies anyone; compare `createCatchupWithPeople` which calls `notifyQuestionsOpen` (`:575-581`)
  - `src/lib/catchups-notify.ts:58-61` (`groupMemberIds`: `findMany` with no `take`, one row per member) and `:187-205` (`notifyReminder` deletes and re-creates one row per member per day)
  - `src/lib/rate-limit.ts:162` (`catchups: { tokens: 5, window: "1 h" }` covers creation and the nudge only)
- Taxonomy: 6j (O(n-members) fanout with n unbounded) · 6h (limit+1 on the roster) · comment-lies
- Expected: spec §4 "`addCatchupMembers` — Keeper, not ended, up to 100 at a time"; the cap's own comment says it bounds reach. The People picker "never offers an existing member", so the UI suggests a roster of about 100.
- Actual: twenty calls of 100 put 2,000 people into one private group in seconds, with no rate limit, no consent and no notification — the first they hear of it is "Answers are open for X's Catch-up" or a daily reminder ("`${name} is waiting on you`" five times an hour via the nudge). Every transition then writes a notification row per member inside the clock's interactive transaction (`catchups.ts:145-230`), and the daily reminder deletes and re-inserts that many rows every morning for a week; `promoteGroupSuccessor` and `pickCatchupPicture` load the whole roster; the People dialog draws every row (T3: the F40 "4,974px column" problem the rework moved off the sidebar).
- Why: the Zod cap is on `userIds.length` of one request. `createMany({ skipDuplicates })` accepts any number of new rows. There is no `count` of `GroupMember` before the insert and no bucket in `rateLimit`. At 2,000 users the Postgres cost is still fine (a 2,000-row `createMany` is tens of ms) — the real costs are consent and the client surfaces.
- Proof: throwaway Keeper (Jerry): call `addCatchupMembers(id, [100 ids])` twice from the console with two disjoint lists; the second returns `added: 100` and the roster is 200. Read-only: none needed, the code is unambiguous.
- Fix direction: enforce `MAX_CATCHUP_PEOPLE` on the roster (count existing + new inside the same transaction as the `createMany`, refuse past the cap with the sentence the picker already knows); put `addCatchupMembers` under the `catchups` bucket; decide whether an added member gets a bell (the docblock already claims one — a `catchup_questions_open`-style "X added you to Y" to the newly added set is the obvious shape) or correct the docblock and the gate's rationale.
- Gate: a lifecycle test that `addCatchupMembers` refuses when `existing + new > MAX_CATCHUP_PEOPLE` and that the action calls `rateLimit("catchups", ...)`.
- Known-related: dedup M12/M29 (the per-call cap and its picker) — this is the per-roster half they left open.

### T2a-04 — Every Catch-up action failure is `console.error`'d and returned as "Something went wrong": the only file in the app that swallows into a log nobody reads
- Severity: Medium
- Confidence: certain
- Where:
  - `src/app/(main)/catchups/actions.ts:229-239` (`runAction`: `catch (err) { if (isMissingCatchupTable(err)) ...; console.error("[catchups/actions]", err); return { error: "Something went wrong. Please try again." }; }`)
  - `src/lib/report-error.ts:1-45` (`reportSwallowed`: "`console.error` on Vercel is a line in a log nobody reads ... Sentry only ever sees what is THROWN") — the fix the engine got for exactly this (C-149, M09) and the actions did not
  - `grep -rn "reportSwallowed\|captureException" src/app --include=actions.ts` → no actions file reports; every OTHER actions file lets unexpected errors throw, where Next's `onRequestError` hands them to Sentry. Only this file catches everything.
  - Concrete paths that land here silently: `openNextEdition` losing the `[catchupId, number]` unique when `nextOpensAt` is null (`catchups.ts:357-396`; the docblock calls the unique "the backstop"), `curatePrompt`'s `delete`/`update` P2025 when a second Keeper removed the question first (`actions.ts:1213-1217`, `:1242`), any P2028 interactive-transaction timeout under pool contention (`max: 5`, `maxWait` 2s), every P2003.
- Taxonomy: 6a (over-broad catch; errors logged then execution continues) · silent-failure lens
- Expected: CLAUDE.md and `report-error.ts`: a swallowed error must reach a human. The engine reports through `reportSwallowed` (`catchups.ts:334`).
- Actual: twenty-two Catch-up actions turn every unexpected exception into the same sentence and a Vercel log line. A Keeper whose "Start the next Edition now" lost a race, or whose "Close and send it out" timed out mid-transaction, is told to try again; the owner never learns it happened. If a schema change breaks one action tomorrow, the member sees "Something went wrong" indefinitely and Sentry stays green.
- Why: `runAction` predates `reportSwallowed` (it was written for the pre-migration P2021 case) and was never updated when C-149 fixed the engine's identical hole.
- Proof: argue-only from the code (deliberately triggering a failure would need a write). A unit pin is enough: `catchup-lifecycle.test.mjs` can assert `runAction`'s body contains `reportSwallowed(`.
- Fix direction: replace the `console.error` with `reportSwallowed("catchups/actions", err, { action })` (pass the action name in; `runAction` is called with a closure, so add a label argument), or re-throw non-P2021 errors and let Next report them the way every other actions file does. Keep the friendly `{ error }` shape either way.
- Gate: the lifecycle test above; `silent-failure` sweep by L4.
- Known-related: C-149 (advanceEdition swallowed with console.error only) — same defect, other half of the feature; not in the baseline for the actions.

### T2a-05 — The next Edition's opening has no tick grace and no civil hour, so the cron misses it about half the time and a dormant group's rhythm slides a day per cycle
- Severity: Medium
- Confidence: certain on the mechanism; likely on the half-the-time rate (it is the same coin flip C-142 measured for deadlines)
- Where:
  - `src/lib/catchups.ts:166-170` (`applyEditionAction`: `nextOpensAt: addCadenceGap(now, meta.cadence)` — the raw publish instant plus the gap, never `snapToDeadlineHour`)
  - `src/lib/catchups.ts:411` (`openNextEditionIfDue`: `if (!opensAt || now.getTime() < opensAt.getTime()) return;` — no `TICK_GRACE_MS`)
  - `src/lib/catchups.ts:473-487` (the sweep's `where`: `nextOpensAt: { lte: now }` — no grace; contrast `sealedDue` three lines above, which adds `TICK_GRACE_MS`, and its comment "The grace is the clock's own, so the query and computeStatus agree")
  - `src/lib/catchups-core.ts:628-651` (`TICK_GRACE_MS`, and its docblock explaining why a threshold minted at one tick's `now` is missed by the next tick "roughly half the time, for any non-zero jitter at all")
  - `src/lib/catchups-core.ts:1272-1274` (`homeStateLine`: "The next one opens ${longDate(nextOpensAt)}")
  - `src/app/(main)/catchups/actions.ts:1382-1386` and `:1422-1426` (`closeAndPublish` stamps the same unsnapped `now + gap`)
- Taxonomy: 6h dates (day boundary, jitter) · 6i crons
- Expected: spec §3.2 "Every deadline lands on 07:00 IST ... picked up within half an hour"; the C-142 fix's own reasoning; the home line promises a date.
- Actual: an Edition the CRON publishes gets `nextOpensAt = 02:00:0x UTC + 1 month`; next month's cron computes `now` at `02:00:0y` and opens the Edition only if `y >= x`. When it loses, the Edition opens on the first member page view after that second (any member's layout runs the scoped sweep), or, for a group nobody visits, at the NEXT day's cron — a day after the date the home page printed. The next publish is then anchored on that late instant, so a dormant group's monthly rhythm walks later by a day per cycle. A Keeper who closes early at 23:00 IST on the 14th books `nextOpensAt` at 23:00 IST on the 14th next month; the page says "opens 14 October", the 14th's 07:30 cron does nothing, and the questions-open bell arrives on the 15th unless somebody visits after 23:00.
- Why: the grace and the snap were applied to `computeStatus` and the two phase deadlines and to the capsule's `publishAt`, not to `nextOpensAt`. The sweep comment even says "the only thing the advance loop below writes to nextOpensAt is now + cadence gap — always in the future", which is the jitter setup.
- Proof: read-only — Batch of 2024's live row: `nextOpensAt = 2026-10-06T01:53:35.048Z` (its publish instant, 02:53 UTC on 09-06, plus a month). This one will be caught by the 02:00 cron on 10-06 because it was published by a page view, not the cron; the miss needs a cron-published Edition. Argue-only otherwise; a unit test on `openNextEditionIfDue` with `now = opensAt - 1s` would fail today.
- Fix direction: (a) compare with the same grace everywhere: `now + TICK_GRACE_MS >= opensAt` in `openNextEditionIfDue` and `nextOpensAt: { lte: new Date(now + TICK_GRACE_MS) }` in the sweep; (b) optionally snap the booked instant to the civil hour (`snapToDeadlineHour(addCadenceGap(...))`) so "opens 15 September" means 07:00 IST on the 15th, picked up by that morning's cron — keep resume's shift unsnapped as designed. Apply to `applyEditionAction`, `closeAndPublish` (both branches), `resumeCatchup`'s re-arm and `updateCatchupCadence`.
- Gate: `catchups-core.test.mjs` "07:00 IST is picked up by that morning's cron" gets a sibling for `nextOpensAt`; a pin that every `nextOpensAt:` write in `catchups.ts`/`actions.ts` goes through one helper.
- Known-related: C-142 (deadline jitter) — dispositioned fixed; this is the same defect on the one threshold the fix did not cover.

## Routed leads (from the coordinator, 2026-09-24) — verdict on each
1. **`updateCatchupCadence` decides from a `nextOpensAt` read before its write** (`actions.ts:743-770`; the `shouldReschedule`/`rescheduled` block at `:749-761`, the unconditional `prisma.catchup.update` at `:758-761`) — **mechanism confirmed, consequence refuted; folded into Verified clean.** If the clock's `openNextEdition` CAS clears `nextOpensAt` between the read and the write, the cadence change re-stamps a date under a freshly opened `collecting` Edition. Nothing then prints it: `homeStateLine` draws "The next one opens …" only when the NEWEST Edition is `published`/`sealed` (`catchups-core.ts:1268-1274`) and the home reads the newest by number (`[catchupId]/(home)/page.tsx:81-84`), the list's `catchupStageLine` says "Open for questions" for a collecting newest; `openNextEditionIfDue` refuses to open while the newest is not published/sealed (`catchups.ts:413-417`), so no double open; `startNextEditionNow` refuses the same way (`actions.ts:1504-1506`); the next publish overwrites the value (`catchups.ts:166-170`). 2. **`extendDeadline` deletes stale reminders AFTER its CAS** (`actions.ts:1569-1576` then `:1583-1590`) — **refuted for every realistic ordering.** The clock's reminder is written under a CAS on `remindersSent: before.remindersSent` inside its own transaction (`catchups.ts:206-215`), and the extend's patch always rewrites `remindersSent` (`extendPhasePatch` re-seeds the daily bucket, `catchups-core.ts:832-838`). Either the reminder's row lock is taken first, in which case the extend's `updateMany` waits, then lands, then its `deleteMany` removes the reminder just written; or the extend lands first, in which case the reminder's CAS no longer matches and nothing is written. The lead's line numbers (1581-1589) are the `deleteMany`.
