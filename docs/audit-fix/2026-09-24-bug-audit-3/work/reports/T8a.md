### T8a-02 — A refund that lands while the gift is "disputed" is thrown away, and a later dispute.won/closed then counts the whole gift again
- Severity: Low (Medium consequence — the public bar and "Given, all time" over-count by the refunded paise for ever, with no audit line — at low probability: it needs a refund to be processed on a payment that has an open chargeback, and the dispute then to resolve in the owner's favour)
- Confidence: possible (mechanism certain from the code; whether Razorpay lets a refund process during an open dispute, and whether it then closes the dispute with `won`/`closed`, is a fact about their product I did not fetch — see Could not verify)
- Where: `src/app/api/razorpay/webhook/route.ts:391-402` (the reversal write: `status: { notIn: [...REVERSED_STATUSES] }` refuses a "disputed" row, `moved.count === 0`, no audit, 200 returned, the refund id never enters `reversalIds`); `:301-336` (the won/closed branch: `unfoldDispute` from the row's `refundedAmount`, which never learned about the refund); `src/lib/contribution-state.ts:159-166` (documents the refund-BEFORE-dispute imprecision, not this one)
- Taxonomy: 6i webhooks out-of-order · 6a state machine hole
- Expected: schema comment on `refundedAmount`: "Paise handed back, cumulative"; `reversalIds`: "The Razorpay refund and dispute ids already folded into refundedAmount"; `unfoldDispute`'s docblock names exactly one imprecision (partial refund, then chargeback, then win) and says the audit line "names the paise so the owner can see what moved".
- Actual: sequence dispute.created (row → "disputed", refundedAmount = amount) → refund.processed for ₹X (refused by the `notIn` guard: dropped, un-audited, not recorded in `reversalIds`) → payment.dispute.won or .closed (row → "paid", refundedAmount = max(0, amount − dispute.amount) = 0). The ₹X that left is counted as given on every surface, and the only trace is a console line nobody reads. A re-delivery of the refund AFTER the win would apply (the row is "paid" again and the id is not in the array) — so the outcome depends on which of two Razorpay deliveries is retried last.
- Neighbours, same branch, recorded so the fix session sees the family: (a) L1-01 (two concurrent distinct reversals, one lost) — not re-reported; (b) dispute.created delivered BEFORE payment.captured (C-151's ordering applied to a dispute): the row goes "disputed" from "created", the capture's CAS then matches nothing and its method backfill matches nothing (`status: "paid"`), and a later `won` resurrects a "paid" row whose `paidAt`, `razorpayPaymentId` and `method` are NULL — excluded from "This month" (`paidAt >= monthStart`), never able to grant a bird pick (`paidAt: { gt: birdPickedAt }`), printed under `createdAt` in the ledger. - Proof: argue-only against the live database (0 reversed rows, 0 reversalIds). A route-level unit test with a mocked `prisma` can prove it in three POSTs with signed bodies (dispute.created, refund.processed, dispute.won) on one row and read `refundedAmount === 0`.
- Fix direction: let a reversal apply to a "disputed" row as well — the `notIn` should refuse only `refunded` (fully returned, nothing left to move), and `foldReversal` on a disputed row should keep `status: "disputed"` while recording the paise and the id, so that `unfoldDispute` can subtract the dispute's own paise and leave the refund's in place. Then `unfoldDispute` needs to know the dispute's paise apart from the refunds' — the docblock already says "Recording it exactly would need a column of its own"; a `disputedAmount Int @default(0)` (or storing per-id paise beside `reversalIds`) is the honest fix and also closes the documented refund-then-dispute imprecision. Write an audit line when a reversal is refused for being out of order, not only when it applies.
- Gate: the mocked-route test above, plus a `contribution-state.test.mjs` case for fold-on-disputed.
- Known-related: C-086 (won disputes count again), C-087 (partial refunds), C-151 (reversal before capture), L1-01. None of them considered a refund landing during a dispute.

## T8a-02, T8a-03 and T8a-04, settled against Razorpay's documentation
Read 2026-09-24, public pages only: razorpay.com/docs/api/disputes/entity, /docs/payments/disputes, /docs/api/disputes/accept, /docs/webhooks/payloads/disputes, /docs/webhooks/payloads/refunds, /docs/webhooks/faqs.

- **T8a-03 as written is refuted; what it was reaching for is confirmed, and it moves T8a-02.** A lost or accepted chargeback does not end in `closed`: accepting "acknowledg[es] it as `lost`" (the sample response shows `"status": "lost"` with `amount_deducted` set), and the disputes guide says `closed` "is seen in fraudulent transactions only". But the same guide defines it as "the state when a fraudulent transaction is closed after you provide details of the transaction or make a refund to the customer", and tells the merchant "In the case of fraud, you must refund the amount". So `payment.dispute.closed` is documented as reachable by money LEAVING, and the route's reading of it ("the chargeback did not stand", route.ts:333) is wrong on that path.
- **T8a-02 is therefore the documented fraud path, not a hypothetical ordering.** Razorpay flags a payment as fraud → `payment.dispute.created` (row → "disputed", `refundedAmount` = the whole gift, although `amount_deducted` "will be `0` unless the status of dispute is updated to `lost`") → the owner refunds, as the guide tells him he must → `refund.processed` arrives while the row is "disputed" and is refused by `status: { notIn: [...REVERSED_STATUSES] }` (route.ts:394): no audit line, its id never enters `reversalIds`, 200 returned so it is never retried → `payment.dispute.closed` → `unfoldDispute` → "paid" with `refundedAmount = max(0, amount − dispute.amount)` = 0 → the refunded gift counts in full on /support and in "Given, all time", beside an audit line saying the chargeback did not stand. The site ends right only if `closed` arrives before `refund.processed`, which is the reverse of cause and effect. The refund payload does carry `payment.entity.order_id` (refunds payload sample), so the route really does reach this branch. Recommendation: T8a-02 Severity Medium (the owner following Razorpay's own instruction produces a permanent public over-count and a false audit line; still needs a fraud flag on a donation, which a signed-in, ₹500-minimum page makes rare), Confidence likely (mechanism certain; the event order is the natural one but not documented). Fold T8a-03 into it; its fix is T8a-02's fix (fold a refund into a disputed row, and unfold only the dispute's own paise).
- **Residual, not verified:** a won chargeback that is re-challenged. The entity doc names the phase — "`pre_arbitration`: A chargeback that you have won is challenged by the customer for the second time" — but none of the pages I read says whether that arrives as a new dispute id or a phase change on the old one. If it is the same id, its second `created` is refused by the `NOT: { reversalIds: { has } }` guard (the id is already there from the first round), the row stays "paid", and the eventual `payment.dispute.lost` — which the route deliberately ignores, pinned by `contribution-state.test.mjs:241` — leaves money Razorpay deducted counted as given. One support question to Razorpay settles it; if it is the same id, acting on `lost` (idempotent on `lost:<id>`, from "paid" or "disputed") closes it.
- **T8a-04's unknowns are answered.** Retries run "in exponential backoff policy 24 hours after event creation"; after 24 hours of continuous failure the webhook is disabled until re-enabled by hand in the Dashboard, and Razorpay emails the Alert Email Address. So the comment at route.ts:98-100 ("the moment RAZORPAY_WEBHOOK_SECRET is set in Vercel, a retry of this same event records it") holds only for events less than 24 hours old, and T8a-04's "no signal on our side" is softened: the owner does get Razorpay's disable email, though nothing on the site says so. T8a-04 stays Low.
- **One more vendor fact, verified clean:** "There could be situations where your server accepts the event but fails to respond in 5 seconds. In such cases, the session is marked timeout" — and retried. The pool's `connectionTimeoutMillis: 5000` means a brownout can push this route past Razorpay's five seconds, but every write in it is a conditional `updateMany` keyed on status and `reversalIds`, so a timed-out delivery that was actually recorded costs one idempotent retry. (The bell in the captured branch is guarded by `moved.count === 1`, so a retry cannot ring it twice.)
- **Capture:** the handler "receives these three identifiers upon payment authorization, not after capture", and "Payments that are not captured are auto-refunded after a fixed time". `confirmContribution` therefore records authorization as "paid". That is right only while the Razorpay account captures automatically — true today (the four `payment.captured` deliveries) and an account setting outside the repo; the Orders API documents no per-order `payment_capture` parameter any more, so the code cannot pin it. Worth one line in the support spec, not a finding.
