### T1-01 — Bold or italic applied to a selection that includes a space publishes as literal asterisks
- Severity: Medium
- Confidence: certain (proved end to end below with the real functions; nothing would change my mind short of the two modules changing)
- Where: `src/lib/rich-text-editing.ts:52-55` (the serializer wraps the run verbatim: `if (inner && isBoldNode(el)) inner = \`**${inner}**\``), `src/lib/rich-text.ts:45-51` (the renderer's `edge = [^\s*]` demands a non-space at BOTH ends of the wrapped run), `src/components/posts/create-post-form.tsx:395-397` (Cmd/Ctrl+B on the live selection), `src/components/common/rich-text-area.tsx` (the edit dialog's field, same serializer)
- Taxonomy: 6h (whitespace edge on a text input), 6a boundary values
- Expected: rich-text.ts:72-74: "the composer serializes live formatting ... to exactly these markers"; rich-text-editing.ts:6: "so bold in one box behaves like bold in every box". What looks bold on the sheet publishes bold.
- Actual: a member selects a word WITH its trailing space (Windows/Chrome double-click selects the trailing space by default; any drag selection can), presses Ctrl+B, sees `hello ` in bold, and publishes. The post reads `**hello **world` with the asterisks visible, in the feed, on the letter page and in every teaser. Same for italic (`*a *b`), underline (`__x __`) and strike (`~~y ~~`), and for a LEADING space (`** hello**`).
- Why: `serializeNode` emits `**${inner}**` wherever the whitespace sits; `emphasisPattern` refuses the pair unless the run starts and ends on `[^\s*]`. Run through the real functions with the test file's own node shim:
  ```
  <b>hello </b>world  => md: "**hello **world" => html: "**hello **world"
  <b> hello</b>       => md: "** hello**"      => html: "** hello**"
  <i>a </i>b          => md: "*a *b"           => html: "*a *b"
  <b>x</b> y          => md: "**x** y"         => html: "<strong>x</strong> y"   (clean)
  ```
  Neither `rich-text-editing.test.mjs` nor `rich-text.test.mjs` has a case with whitespace at a formatting edge: every pinned case is `<B>[text("bold")]`.
- Proof: read-only, done above (pure functions). Live, throwaway account: in the feed composer type `hello world`, drag-select `hello ` (word plus space), Ctrl+B, Post. The card shows `**hello **world`.
- Fix direction: in `serializeNode`, move leading/trailing whitespace of a formatted run OUTSIDE the markers (`**hello** `), the normalisation every markdown editor performs; leave the renderer's strictness alone (its comment argues for it). Add the four shim cases and a serialize-then-render round-trip test.
- Gate: `src/lib/rich-text-editing.test.mjs` (`<b>hello </b>` serializes to `**hello** ` and renders `<strong>hello</strong> `).
- Known-related: none in the baseline. The owner's 2026-08-27 doubled-blank-line report was this serializer, a different rule.

### T1-02 — "Save as draft" on a fresh letter, while the writer keeps typing, creates a SECOND draft on the way to the edit page (and the two name the same photographs)
- Severity: Medium
- Confidence: likely (mechanism certain from code; the trigger is a keystroke during the save's round trip, which a slow phone connection stretches to seconds)
- Where: `src/components/posts/create-post-form.tsx:518-531` (`markSaved()` then `onDraftSaved(result.postId)`), `:570-576` (`finally` clears `submittingRef` synchronously), `:631-643` (the contentEditable is never disabled while saving), `src/components/letters/letter-desk.tsx:118-122` (`router.replace(\`/letters/${id}/edit\`)`), `src/components/posts/use-letter-persistence.ts:385-386` (`exitRef` tracks live content), `:387-442` (the unmount exit-save: `if (s.postId) editPost … else createPost(saveAsDraft)`), `src/app/(main)/feed/actions.ts:241-266` (the twin guard matches on exact content)
- Taxonomy: 6b (effect cleanup / stale closure), 6c(1) double-invocation, 6i double-submit on a form
- Expected: use-letter-persistence.ts:381-383: "unmounting because a save or a publish just navigated writes nothing"; letter-desk.tsx:118-120: "Adopt the new row: from here on, saves update in place".
- Actual: press Save as draft on `/letters/new`, type a few more characters while "Saving..." is up, land on `/letters/<id>/edit` holding the OLDER text, get a second toast "Saved to your drafts", and find two drafts of the same letter in the strip on /letters, the newer words in the one not being edited. Both rows carry the same `images` JSON.
- Why: `markSaved` records the snapshot of the content that was SUBMITTED (correct). `onDraftSaved` triggers `router.replace` to a sibling route segment, which unmounts the `/letters/new` desk; by then `finally` has cleared `submittingRef` and `exitRef.current.content` holds the newer text, so the snapshot check at :398 fails and the exit-save runs. The unmounting hook instance was created with `postId === undefined` (it is the `/letters/new` page's), so :431-434 takes the `createPost` branch with `saveAsDraft`. The server twin guard compares `content` exactly and the content differs by the new keystrokes, so a second row is created.
- Proof: throwaway account, devtools throttling "Slow 3G", `/letters/new`, type a sentence, press Save as draft, type three characters before the toast. Observe two toasts, the shorter text on the edit page, two drafts in the strip. Read-only confirmation: `SELECT id, left(content,40), images, "createdAt" FROM "Post" WHERE "authorId"=<jerry> AND status='draft' ORDER BY "createdAt" DESC LIMIT 2`.
- Fix direction: let the hook learn the row it just created (an `adoptRow(id)` the composer calls on `createPost` success, stored in a ref the exit-save reads instead of the `postId` prop) so the exit-save becomes an in-place `editPost` with the new base version; and never let the exit-save `createPost` for a letter whose row already exists.
- Gate: extract the exit-save decision ("which write, if any") into a pure function pinned by `node --test`; a Playwright spec for the throttled flow.
- Known-related: C-177 (exit save) and C-175 (autosave vs publish) built this seam; neither covers create-then-navigate. See T1-16 for what the duplicate does to the photographs.

### T1-03 — Leaving the desk while an autosave is in flight fires a second save with the same version token, and the loser tells the writer the letter did not save

- Where: `src/components/posts/use-letter-persistence.ts:295-309` (`autosaveRunRef.current = runAutosave()`), `:387-442` (the exit-save reads `baseUpdatedAtRef` and never awaits `autosaveRunRef`), `:138-141` (the comment: "An explicit Save or Publish waits for it before sending its own version token" — the exit-save is the third writer and does not), `src/app/(main)/feed/actions.ts:604-611` (`updateMany where updatedAt: base` refuses the second)
- Taxonomy: 6c(3) out-of-order completion, 6i two surfaces mutating one row
- Expected: :371-373 "Nothing is lost by leaving"; M66's guard exists so "nobody's writing is destroyed".
- Actual: pause 2.5s (autosave fires), then within its round trip click "All letters". It is kept on this device." appears on the letters index while the row does hold the text. If the autosave loses, `writeLocalDraft()` leaves a stale device copy that is offered back next visit as "a newer copy of this letter".
- Why: `handleSubmit` awaits `autosaveRunRef.current` before sending (create-post-form.tsx:437) precisely to avoid this; the unmount cleanup at :393 does not, and a cleanup cannot await, so it must chain onto the in-flight promise or skip when the in-flight payload already equals the exit snapshot.

- Fix direction: `const inFlight = autosaveRunRef.current; (inFlight ?? Promise.resolve()).then(() => { if the snapshot now equals savedSnapshotRef return; editPost with the base the autosave produced })` — the refs are shared, so the chained call sees the new `baseUpdatedAtRef`.

- Known-related: C-175 (autosave vs publish) got `disarmAutosave` plus the await; autosave vs exit got neither.

### T1-04 — editPost reads the row version back in a second statement, so with two devices saving at once the returned base can be the OTHER device's and the next save silently overwrites its words
- Severity: Medium
- Confidence: possible (mechanism certain; the window is milliseconds between two statements)
- Where: `src/app/(main)/feed/actions.ts:604-627` (`updateMany where { id, authorId, updatedAt: base }` … then `prisma.post.findUnique({ select: { updatedAt } })`), `src/components/posts/use-letter-persistence.ts:333` (`baseUpdatedAtRef.current = result.updatedAt`)
- Taxonomy: 6c(2) read-modify-write, 6i two surfaces mutating one row
- Expected: :580-590 "If the row has moved on since, nobody's writing is destroyed".
- Actual: A and B both hold v2. A updates v2→v3; before A's re-read, B (base v2) is refused — fine. But if B had adopted v2 from its OWN earlier save and then A and B race: A writes v3, B's write lands v3→v4 before A's re-read (B's base was v3? only if B saved between). The reachable case: A writes v3; A's `findUnique` runs after B's successful v3→v4 (B had adopted v3 from its own re-read of A's write... ) — in short, whichever device re-reads last adopts the other's version and its next save destroys the other's text. The trigger needs both to be saving within one round trip, which two open tabs of one draft on a laptop and a phone do every 2.5s of typing.
- Why: the version handed back is not the version this write produced; it is whatever the row holds a statement later.
- Proof: argue-only live. A deterministic pin is the code-shape gate below.
- Fix direction: return the version from the write itself: `tx.post.update({ where: { id, authorId, updatedAt: base }, data, select: { updatedAt: true } })` (Prisma's extended where-unique accepts non-unique fields beside `id`) and treat P2025 as "moved"; or a raw `UPDATE … RETURNING "updatedAt"`.
- Gate: a rule test that `editPost` takes `updatedAt` from the update statement (no `findUnique` after the write).
- Known-related: M66 introduced the guard; this is the guard's own re-read.
