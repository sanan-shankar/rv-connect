# C6 — what a signed-in member can make the server write, send or spend
Agent: C6 · Started: 2026-10-24 · Model: Opus 5.5 (1M)
Charter: the authenticated twin of C5's anonymous sweep. Every server action and API route a
signed-in account can call, at each trust stage (Stage 0 unconfirmed, Stage 0 with confirmation
queued, Stage 1 confirmed-unvouched, Stage 2 verified, teacher, Keeper, supporter): what it writes
(rows, R2 objects, bells and mail fanned out to other members, link-preview fetches, Upstash
commands), what bounds it per member / per stage / globally, what a looping script holding one
cookie costs, and how long the writes are kept. Then the gaps: unmetered repeatable writes that fan
out to other members, grow a table or the bucket without bound, or spend a shared budget. New
defects only. HEAD read: 36ed27d3 (at start; no commit landed during the round).

## The table — signed-in callables: what each makes the server do, write, send and keep

Conventions. **Stage** is the lowest tier that reaches the write (`member-gate.ts:17-21`: Stage 0 =
account, email unconfirmed; Stage 1 = confirmed, OR "Stage 0 with confirmation queued", which
`emailGateOpenFor` lets through every Stage 1 gate since d7a8041d; Stage 2 = verified). Teachers and
supporters hold no capability a Stage 2 alumnus lacks except where noted; a Keeper is a Stage 2
member with a hat, and on a batch Catch-up every member holds the cycle verbs (daec81ec, L10-01).
**Meter** = the Upstash bucket (`rate-limit.ts:36-201`, one EVALSHA per allowed call) or a DB count.
"none" means nothing per member bounds a script calling it in a loop except the function's own
latency. Upstash cost is only on metered calls; ephemeral-cache refusals on a warm instance are free
(C5 verified). Retention from `retention.ts:26-60` (notifications 30 d unread / read past the 100th
nightly; Visit + SearchLog 90 d; OutboundEmail 180 d; LoginAttempt + AuditLog 365 d; AdminMessage
730 d; Report 1,095 d; Contribution 3,650 d; everything else: until the account purge).

## Findings

### C6-01 — Any signed-in account, confirmed or not, can make the site mail its own never-proven address eight times an hour, and the "scheduled for deletion" half is a reserved, priority kind: two accounts take every day's 95 mails, so no new member's confirmation goes out again and every reset waits for 05:30 IST
- Severity: Medium (a deliberate actor, but the cost is one or two signups and a password; the consequence is the C5-02 outage reached by a door C5-02's fix does not touch, made permanent rather than daily, and aimed at any inbox the attacker names)
- Confidence: certain on every bound below (constants and the drain's order read at source; `eligibleKindsFor`/`PRIORITY` run pure in /tmp: `eligibleKindsFor(0)` → `["reset","password-changed","deletion-scheduled"]`); likely on the spam-complaint consequence (Resend's policy, L8 §0.4). What would change my mind: a per-address or per-day ceiling somewhere between `enqueueMail` and the provider — I found none (`email-queue.ts:457-524` is the only gate; `claimAndSend`/`render` add none, `:578-621`).
- Where:
  - `src/components/auth/email-actions.ts:42-80` — `resendVerification` takes no arguments, refuses only a CONFIRMED account (`:70`), then `sendVerificationEmail` → `enqueueMail({ kind: "verify", to: session.user.email })` (`src/lib/verification-mail.ts:22-36`). Nothing else bounds it.
  - `src/components/settings/actions.ts:181-256` — `requestAccountDeletion`: no confirmation gate; the password is checked (`reauth` spends on WRONG passwords only, `:204-210`); `credentialVersion: { increment: 1 }` (`:221`) ends the session; then `enqueueMail({ kind: "deletion-scheduled", to: me.email, ... })` (`:240-256`) to whatever address the row holds, proven or not.
  - `src/lib/auth.ts:268-290` — the next password sign-in is the cancel gesture (clears `deletionRequestedAt`, writes an AuditLog row and a bell) and imposes no wait, so request → sign in → request is a loop. A sign-in with no Turnstile token still passes on `login-unverified`, five an hour per IP (`rate-limit.ts:70`, `auth.ts:138-185`), so one account's three cycles an hour need no browser at all; a second account needs a second IP or a real browser (where Turnstile usually passes without a click).
  - `src/lib/email-queue.ts:435-442` — the ONLY per-account bound, hourly: `verify: { max: 5, windowMinutes: 60 }`, `"deletion-scheduled": { max: 3, windowMinutes: 60 }`; `:466` only `verify` and `reset` fold, so queued deletion notices accumulate one row each; `src/lib/auth-tokens.ts:52-59` the mint ceiling's comment: "Stops this from being used to flood somebody's inbox, and stops a script from burning the sending quota" — 5 an hour is 120 a day against an 85-a-day confirmation share.
  - `src/lib/mail-policy.ts:26-34` (`"deletion-scheduled": 20`, ahead of `verify: 100`), `:46-48` (`RESERVED_KINDS` = every kind but verify: "the ones that may spend the daily budget all the way down"), `:57-59`; `src/lib/email-queue.ts:87` (`DAILY_CAP = 95`), `:103` (`RESET_RESERVE = 10`), `:816` and `:839` (eligible kinds by the reserve line, then `orderBy: [{ priority: "asc" }, { createdAt: "asc" }]`).
- Taxonomy: 6j (third-party quota under load — Resend's 100/day; the only shared mail budget), 6k (provider pause after complaints), 6h identity states (Stage 0 and "Stage 0, confirmation queued"), comment-that-lies (`auth-tokens.ts:52-55`, `rate-limit.ts:71-74` "every account it mints is Stage 0, which can write nothing")
- Expected: `email-queue.ts:428-433` — the enqueue limit "guards how much of a shared 100-a-day budget one person can consume. Without it, holding down 'resend' on launch day is a denial of service against everyone else's welcome email"; the reserve exists so "the first person who forgets their password that afternoon" can get back in (`:89-93`).
- Actual: from one signed-in, never-confirmed account (any address typed at signup — the attacker's, or a stranger's): `resendVerification` 5 times an hour, plus the delete/sign-in cycle 3 times an hour, is 8 sends an hour, all accepted at once while the day has budget. One account empties the 85 confirmation slots in ~10.6 hours and the 10 reserved ones ~3 hours later; four accounts do it in ~3.5 hours. Two accounts cycling deletion alone queue 6 reserved notices an hour, 144 a day, more than the whole budget: overnight their rows pile up (not folded), and at 00:00 UTC the drain sends resets first, then THESE (priority 20), and only then confirmations (100) — of which none are reached. From then on, every day: no new member's confirmation is ever sent; a member who presses "Send it again" with the gate shut waits for ever; a reset asked for after the morning's drain waits until the next 05:30 IST. Side effects: (1) while confirmations wait, `confirmationStillWaiting` opens every NEW account's Stage 1 gate without a mailbox (d7a8041d's rule), so the attacker's own later signups with invented addresses read names, batches and profiles; (2) nobody who joins in that time is confirmed, so the roster cannot verify them (`roster.ts:56`, auto-verify needs `emailVerified`) unless they happen to use a password reset, which confirms as a side effect — the intake piles onto the owner by hand; (3) the target inbox receives every send the loop wins, up to the whole day's ~95 "Confirm your email" and "Your Rishi Valley account will be deleted" mails from the site's domain, every day; one spam complaint at this volume (~600 sends a month in total today) is above the 0.08% Resend quotes, and a sending pause stops resets too.
- Why: every bound is per ACCOUNT per HOUR, the budget is per SITE per DAY, and `deletion-scheduled` was made a reserved kind (correctly, as a takeover alarm for a real member) without asking whether the address had ever been proven. An unconfirmed account has no mailbox to protect, so the alarm protects nobody and the reserve protects nothing from it.
- Proof: arithmetic from the constants above; the pure run of `eligibleKindsFor`/`PRIORITY`. Read-only baseline (`OutboundEmail` by kind/status): 597 verify sent, 22 reset, 18 password-changed, **2 deletion-scheduled ever**; peak day 88 sends (2026-10-02), so organic traffic alone already reaches the cap on a busy day and the attack is everything above it. A live demonstration would send real mail; argue-only. A unit pin is possible with `enqueueMail` stubbed: 24 hours of one user's verify + deletion enqueues are all accepted today (192 rows).
- Fix direction: (1) one per-RECIPIENT ceiling across all kinds per rolling 24 h in `enqueueMail` (the bound an attacker cannot multiply with accounts or IPs; also closes C5-02); (2) never send `deletion-scheduled` (or any security notice) to an address that was never confirmed — record the request and stop; (3) fold `deletion-scheduled` like verify/reset, so a queued notice absorbs the next request; (4) a per-account DAILY verify ceiling (e.g. 3 after the first) and correct the two comments; (5) consider a cool-down on re-requesting deletion right after a cancel.
- Gate: a `mail-policy` test that for any one address the kinds together cannot exceed K a day; a source pin that `requestAccountDeletion` does not enqueue for an unconfirmed row.
- Known-related: C5-02 (same budget, the anonymous reset door — its fix direction is reset-only and leaves this open), C-161/L3-01 (natural backlogs), T5-13 (the resend reports "sent" when refused), T6-08 (the deletion cancel flow), L8 §0.4 (Resend's complaint threshold).

### C6-02 — One verified account can ring every member's bell as often as it likes: the 20-a-save mention cap is per SAVE and `editPost` has no meter, and every bell dedupe keys on the sender's current name, which is free to change
- Severity: Medium (needs a Stage 2 account acting deliberately or hijacked — which is exactly the threat the meters exist for, `rate-limit.ts:31-33` "these only need to cap what a hijacked or misbehaving VERIFIED account can do per unit time"; the reach is the whole community and the Notification table, and nothing but an admin's block stops it)
- Confidence: certain on the mechanism (every line below read at HEAD; the dedupe and the cap are pure logic over the stored rows); the throughput figures are estimates from the statement count, not measured. What would change my mind: a meter on `editPost` or a per-recipient ceiling on mention/like bells somewhere I did not find (grep for `rateLimit(` lists 22 call sites, none in `editPost`, `publishDraft`, `toggleLike`, `toggleCommentLike` or `updateProfileField`).
- Where:
  - `src/lib/mention-notifications.ts:26-36` — `MAX_MENTION_NOTIFICATIONS = 20`, argued as "keeping one save from paging half the community"; `:77-79` the slice to 20 per call; `:107-121` — the dedupe the authors added for exactly this action: "editPost has no rate limit, and its diff only compares a save with the one before it, so taking a tag out and putting it back, save after save, would ring the same person every time" — keyed on `{ userId, type: "mention", message, link }` where `message = \`${opts.actorName} mentioned you in a ${noun}\`` (`:113`)
  - `src/app/(main)/feed/actions.ts:585-593` (`editPost`: Stage 2 gate, no `rateLimit`), `:783-801` (`newIds` = ids in this body not in the previous body, handed to `notifyMentioned` with `actorName: session.user.name`); `:157` the `posts` meter is on `createPost` only; `:310` the create path, `:424` `publishDraft`
  - `src/lib/post-notifications.ts:52-59` (`notifyMemberOnceUnread` matches `{ userId, type, message, link, read: false }`) with `feed/actions.ts:873-878` (`message: \`${session.user.name} liked your …\``) and `:1401-1406` (the comment-like twin); `toggleLike`/`toggleCommentLike` are unmetered (`:820-829`, `:1372-1380`)
  - `src/components/profile/profile-actions.ts:100-128, 241` — a name change: any 2-100 characters, unmetered, no audit row; `src/lib/auth.ts:375-389` re-reads `name` on every session read, so the next request carries it; `src/lib/roster.ts:56-57` the roster re-run on a name change only ever verifies, so renaming costs the account nothing
  - `src/lib/rich-text.ts:24` — a mention is `@[anything](id)`; the display name is not checked against the id, and the ids are on every profile link a Stage 1 account can list
  - growth: `src/lib/retention.ts:126-127` (30 days, by age) and `:241-260` (the per-member cap deletes only READ rows past the 100th) — an unread flood stays 30 days
- Taxonomy: 6j (O(n-members) fan-out with no per-member bound), 6c (an unmetered write that reaches other members), comment-that-lies (`mention-notifications.ts:31-34`), 6j unbounded table
- Expected: the owner's mention rule ("notify the person who is tagged"), bounded the way its own comments say: no save pages half the community, the same person is told once, a like is "one notification per person per thing, not one per tap" (audit M33, `post-notifications.ts:33-46`).
- Actual: (a) **every member, once a post, unmetered.** A Stage 2 account publishes a post (60 an hour allowed), then saves it with 20 mentions, then with 20 different ones, and so on: each save's `newIds` are the 20 not in the previous body, so each save rings 20 new people. 575 members take ~29 saves, a few seconds of script. Next post, again: 60 × 575 ≈ 34,500 bells an hour. (b) **unbounded with a rename.** The "told once, ever" lookup matches the whole sentence, which carries the author's CURRENT name: `updateProfileField("name", "Jerry Maguirf")`, and every member is "new" again on the same post. Same for likes: rename → unlike → like rings the author again ("X liked your post" is a different row from "Y liked your post"), so one member's bell can be filled at function speed, which is the precise M33 behaviour the helper exists to stop. Each `editPost` is ~25 sequential statements (`notifyMentioned` does up to 20 `notification.create` round trips, `:122-134`), so a single sequential script rings on the order of 100+ members a second. At ~350 B a Notification row with its three indexes (live: 563 rows, 194 B average tuple, indexes on `id`, `(userId, read)`, `(userId, createdAt)`), (a) alone is ~12 MB an hour and (b) is in the hundreds of MB an hour — the 500 MB billing quota and the 2 GB disk's read-only line (`snapshot.mjs:178-190`) are hours to days away, and every member's bell shows hundreds of "Jerry mentioned you in a post".
- Why: the 2026-09-27 write-path review saw the unmetered edit and closed the one loop it imagined (the same person, tag out and back); rotating through DIFFERENT people and changing one's own name were not imagined, and the dedupe chose the rendered sentence as its key because `Notification` has no sender column (`catchups-notify.ts:373-380` says so for the Catch-up twin).
- Proof: argue-only live (any demonstration rings real members). Read-only: `Notification` has 0 `mention` rows today (the feature is new) and 575 users. The pin is a unit test: `notifyMentioned` called twice for the same post with the same ids and two different `actorName`s writes two rows per member today; called 29 times with disjoint 20-id lists it writes 575.
- Fix direction: (1) meter `editPost` (and `publishDraft`) — the `posts` bucket or a cheaper "edits" bucket — or meter the BELLS: a per-actor ceiling on mention bells per hour/day, checked in `notifyMentioned`; (2) key the dedupe on the SENDER, not the sentence: add `actorId` to `Notification` (nullable, indexed with `userId`) and dedupe likes, mentions and Catch-up comment bells on `(userId, type, actorId, link)`; (3) a per-post lifetime ceiling on distinct members mentioned (e.g. 20 across all saves), which is what the 20-a-save comment promises; (4) audit or throttle name changes (one a day is plenty) — the same free rename also defeats T2a-02-style "who did this" reading of old bells.
- Gate: a unit test that a second `notifyMentioned` call on the same post with a changed `actorName` writes nothing; a source pin that `editPost` passes a meter; a test that a post's distinct mentioned-and-told members cannot exceed N across saves.
- Known-related: V-L-b-01 / C3's Extends (the mention bell's ordering and the `publishDraft` double-run — a different defect), T2a-03 (the Catch-up add door, same "reach without a meter" class), M33 (audit 1, the like dedupe this defeats), L6-02 (bidi text in names reaching bells — the rename here is the same field).

### C6-03 — An account that never confirms its email can store about 86 MB a day of private letter drafts, for ever: the draft exemption has a rate but no ceiling, so the signup meter's premise that a Stage 0 account "can write nothing" is false
- Severity: Medium (a deliberate actor with cheap accounts; the consequence is the database's billing quota and then its read-only line, which stops every write for everyone; the nightly 350 MB alarm gives about a day's notice per few hundred MB)
