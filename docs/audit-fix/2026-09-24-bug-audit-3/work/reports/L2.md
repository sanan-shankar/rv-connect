## Revalidation map — summary (every mutation → what it purges → what stays stale)
- No `revalidateTag`, no `unstable_cache`, no `"use cache"` anywhere in `src` (grep, 2026-09-27), so there is no data-cache layer and no cross-user cache to poison. All caching of per-user reads is React `cache()` (request-scoped only).
- No full-route cache exists (root layout is dynamic), so `revalidatePath` here has two real effects: (1) in a Server Action response it flags the response as revalidated, which re-renders the current route from the root and refreshes the ACTING user's client Router Cache; (2) it clears matching entries from the acting user's client Router Cache so their NEXT navigation refetches. It does NOT push to any OTHER member's browser.
- Layer purged vs left stale, by call site: `revalidatePath(path)` purges the page segment; `revalidatePath(path, "layout")` purges the layout too. The admin rail (computed in the layout) is the one surface where the distinction bites → L2-02. Everywhere else, because pages are dynamic and refetch on navigation with `staleTimes.dynamic = 0`, a page-type revalidation is sufficient for the acting user; the risk is only "another member's already-open browser does not update", which is inherent to revalidatePath (not a push) and is a design fact, not a bug — the app leans on `router.refresh()` after the actor's own writes for the actor's own view.
