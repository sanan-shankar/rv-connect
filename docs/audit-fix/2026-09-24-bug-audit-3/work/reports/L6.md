# L6 — input validation and the naughty strings (lens)
Agent: L6 · Started: 2026-09-24 08:43 BST · Model: Opus 5.5 (claude-opus-5-5)
Charter: every input a member or an admin can reach — form fields, action arguments, route params
and search params, JSON bodies, webhook bodies — traced from its client cap to its server schema to
its column to every place it is drawn. Three jobs: (1) the whole-app input inventory and the
client/server/column cap-mismatch table; (2) the two classes the live pass proved (NUL refused by
Postgres, bidi controls stored and rendered raw) extended statically to every write path and every
member-to-member render, together with the zero-width class that `trim()` keeps; (3) the Big List
of Naughty Strings plus synthetic hostile strings EXECUTED through every pure input-processing
function, imported from its real source file, with per-function results. Read-only; no scratch file
was ever written (every script ran from stdin; the two early runs that used `/tmp` deleted their
folder in the same command, and `ls /tmp/l6-*` is empty).

Two facts frame everything below:
- **No string column in this database has a length limit or a CHECK on its content.** There is not
  one `@db.VarChar` in `prisma/schema.prisma`; every `String` is Postgres `text`. Every cap in the
  app lives in code, so a writer that forgets one is uncapped all the way to the 25 MB action body
  (`next.config.ts:328-329`).
- **Nothing on any write path removes a control, bidi or zero-width character.** The only code in
  `src/` that touches U+0000 or the invisibles is `rich-text.ts:97` (drops NUL on the Catch-up link
  path only), `link-preview-core.ts:357` (`tidy`: C0 to space, for third-party page titles),
  `next-path.ts:23` (refuses C0 in `?next=`), `caption-tidy.ts:46` (drops ZWSP/ZWNJ/ZWJ/BOM, applied
  only in the admin review room's editable box) and `magazine/measure.ts:31-48` (the print
  magazine's `visibleText`). No `.normalize("NFC")` runs on any member text either (only
  `city-coords.ts:108` and `roster-rule.ts:21` fold for matching).

## Findings

### L6-01 — Editing a post, letter draft or answer that contains an @-mention silently turns every mention into plain text
- Severity: Medium
- Confidence: certain on the mechanism (executed against the real serializer and renderer); likely on the member hitting it (needs a mention, then any later edit). What would change my mind: a mention-aware branch in `serializeNode` that I missed — there is none (`rich-text-editing.ts:33-58` handles text, BR, DIV/P and the four emphasis tags, nothing else).
- Where: `src/lib/rich-text.ts:133-136` (a stored `@[Name](id)` becomes `<a href="/profile/id">@Name</a>`); `src/lib/rich-text-editing.ts:33-58` (`serializeNode`: an `<a>` is not a block and not bold/italic/underline/strike, so it returns only its inner text, `@Name`); the four hydration sites that feed stored markdown back into an editor as HTML: `src/components/common/rich-text-area.tsx:58` (`el.innerHTML = renderRichText(initialValue)`), `src/components/posts/create-post-form.tsx:259` (resumed draft) and `:270` (device copy restored); the saves that follow: `rich-text-area.tsx:65-70` (`onChange?.(serializeEditableToMarkdown(el))` on every input), `create-post-form.tsx:370-374` (`setContent(serializeEditableToMarkdown(el))`), `src/components/posts/edit-post-dialog.tsx:43,48-51,97-100` (the dialog posts whatever the editor last serialized), `src/app/(main)/feed/actions.ts:595-600,619-624` (`editPost` writes `content` as sent). Surfaces: `/letters/[id]/edit` (`letters/[id]/edit/page.tsx:65` → `letter-desk.tsx:112` → `create-post-form`), the published post/letter edit dialog (`letter-menu.tsx:214`, the feed card's edit), and the Catch-up answer card (`answer-card.tsx:114-116`).
- Taxonomy: 6h (round trip of member text), L9 (comment lie)
- Expected: `create-post-form.tsx:251-253`: "renderRichText is the same markdown -> HTML bridge the reading page uses, and serializeEditableToMarkdown is its inverse, so the draft round-trips." `rich-text-area.tsx:12-15`: "renderRichText hydrates it once on mount and serializeEditableToMarkdown mirrors every input back — so anything already storing plain text keeps working unchanged".
- Actual: a member writes "Thanks @[Asha Rao](cm…) for this" (the composer inserts that text node itself, `create-post-form.tsx:409`), saves the draft, comes back, and types one letter anywhere. The autosave stores "Thanks @Asha Rao for this": the link to Asha's profile is gone for every reader, for good, and nothing on screen changed (the editor showed "@Asha Rao" as a green link a moment ago; the next reload shows plain text). The same happens to every mention in a published post the moment its author opens "Edit" and changes a comma.
- Why: the serializer is the inverse of the renderer for emphasis only. Executed through the real modules with a minimal DOM (text/element nodes exactly as the browser's parser produces them from the renderer's output): `"Thanks @[Asha Rao](cmabc123) for this"` → render → `Thanks <a href="/profile/cmabc123" class="…">@Asha Rao</a> for this` → serialize → `"Thanks @Asha Rao for this"`; `"**@[Asha](cm1)**"` → `"**@Asha**"`. Of 600 corpus strings round-tripped (BLNS + synthetic), exactly the four carrying mention markup changed (plus a leading-newline artefact of the harness); every emphasis form, entity and HTML payload came back byte-identical.
- Proof: argue-only against members' data (live: `SELECT count(*) … WHERE content ~ '@\[[^]]+\]\([A-Za-z0-9_-]+\)'` is 0 for Post, drafts, Comment and CatchupEntry today, so nothing has been damaged yet). A unit test proves it: build `<div>` → text `"@[A](x)"`, run `renderRichText`, parse, `serializeEditableToMarkdown`, expect the input back. It fails today.
- Fix direction: make the pair an inverse for mentions. Either the renderer marks a mention anchor (`data-mention-id`) and `serializeNode` re-emits `@[${text.slice(1)}](${id})` for it, or the editors hydrate with a renderer mode that leaves mention markup as text (the composer already shows mentions as raw `@[Name](id)` text while typing). Then correct both comments.
- Gate: a round-trip property test in `rich-text-editing.test.mjs` over the same corpus: for every input, `serialize(parse(renderRichText(md))) === md`.
- Known-related: T1-01 (bold with trailing space — the serializer's other asymmetry, found by T1); T1-19 (mention picker regex). Neither is this.

### L6-02 — A bidi override in a name, a Catch-up name or a message runs into the app's own sentence in other members' bells and admin inboxes (the whole-app extension of V-O-B)
- Severity: Low (rides V-O-B's ruling; the sentence is garbled, not hidden, and a member must type the control on purpose)
- Confidence: certain on the mechanism (every schema accepts U+202A–U+202E and U+2066–U+2069 — executed, 6–7 of 536 corpus lines per field keep them after parsing; nothing strips them; the bell renders one text run). V-O-B proved the name half live.
- Where: the sinks where a member-supplied string is interpolated into an app-authored sentence that another person reads, all rendered as one React text node with no `<bdi>`, `dir="auto"` or `unicode-bidi: isolate` (`src/components/layout/notification-bell.tsx:479` `<p className="text-sm text-foreground">{notif.message}</p>`):
