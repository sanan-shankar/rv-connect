## Facts this report leans on (each read in the installed source, not assumed; re-checked at HEAD)

1. **Server actions from one tab run strictly one at a time.** Next is 16.3.8 at HEAD (df260031);
   `node_modules/next/dist/client/components/app-router-instance.js:50-165` (`runRemainingActions` / `runAction` /
   `dispatchAction`): a second `ACTION_SERVER_ACTION` is appended to `actionQueue.last` and started only when the
   previous action's reducer promise has settled, and `server-action-reducer.js:205-263` awaits the whole HTTP
   response before settling. So two awaited server actions from one tab can never overlap on the server or answer
   out of order. The one exception is a NAVIGATION (`ACTION_NAVIGATE`/`ACTION_RESTORE`, `:147-160`): it marks the
   pending action `discarded` and runs at once; the discarded action's own promise still resolves
   (`resolve(actionResult)` at `server-action-reducer.js:263` is independent of the queue), and the actions queued
   after it run once the navigation settles, so they CAN overlap the discarded one. Consequences used below: (a)
   6c(3) "out-of-order completion" between two server actions in one tab is structurally impossible; it survives
   only across a navigation, across tabs, and for `fetch()` to route handlers (L7-09 is a `fetch` chain); (b) any
   "response A re-renders before action B has even started" window is certain, not a race (this upgrades T3-24's
   flicker, see Seeded leads); (c) a slow action delays every later action from that tab.
2. **Tailwind 4.2.2 puts every `hover:`/`group-hover:` inside `@media (hover: hover)`** (T3-19 verified in
   `node_modules/tailwindcss/dist/lib.js`), and `scale-*`/`translate-*`/`rotate-*` set the standalone CSS
   `scale`/`translate`/`rotate` properties, which an explicit `transition-[…,transform]` list does not name, and
   which `transition-colors`/`transition-opacity` do not include (TRAPS "Testing", measured live by a past
   session). `transition`, `transition-transform` and `transition-all` do include them.
3. **Base UI's `DialogPopup` stops propagation of the composite keys** (ArrowUp/Down/Left/Right, Home, End) at the
   popup (`@base-ui/react@1.3.0` `esm/dialog/popup/DialogPopup.js:91-95`, `esm/composite/composite.js:15`); other
   keys reach a `window` listener.
4. **`motion` renders `initial` into the server HTML.** A cookieless `curl http://localhost:3000/login` returns
   `style="opacity:0;transform:translateX(48px)"` on the login column, from `m.div initial={{ opacity: 0, x: 48 }}`:
   the same root `LazyMotion` every page renders under (re-run read-only 2026-10-23, same answer). Until the async
   `domMax` feature chunk loads (`common/motion-features.tsx:37-40`), an `m.*` element cannot animate away from
   `initial`, and `LazyMotion`'s `features().then(...)` has no `catch` (framer-motion 12.38.0,
   `dist/es/components/LazyMotion/index.mjs:55`; T8b's erratum).
5. **The landing showcase is dormant.** `src/app/page.tsx:31-38` renders `<LandingHero>` only; the import of
   `showcase` exists only inside a comment (`:24-25`). `showcase.tsx`, `landing-nav.tsx`, `landing-footer.tsx`,
   `footer-hoopoe.tsx`, `perching-birds.tsx`, `ambient-leaves.tsx`, `section-reveal.tsx`, `feature-section.tsx`,

6. **No React Compiler.** `next.config.ts` has no `reactCompiler`, `package.json` no `babel-plugin-react-compiler`,

7. **(new) An error thrown by a component the `(main)` LAYOUT renders is caught by the root `src/app/error.tsx`,

## Findings

### L7-01 — Every signed-in page, and the loading skeleton meant to paint first, is invisible until JavaScript and the motion chunk have arrived; if that chunk fails, every page of the app stays blank for the session
- Severity: Medium
- Confidence: certain on the mechanism (the wrapper's server style is the library behaviour proved on /login,
  and the hierarchy is Next's documented one); likely on how long the blank lasts on a real phone (not
  measured; it is the JavaScript hydration time of the route plus one more chunk). What would change my mind:
  a signed-in `curl`/view-source of `/feed` showing the page region without `opacity:0` (I may not sign in).
- Status at HEAD: OPEN, unchanged (`template.tsx` and `motion-features.tsx` untouched since 495ecdd2).
- Where: `src/app/(main)/template.tsx:27-37` (`<m.div className="flex min-h-0 flex-1 flex-col" initial={{ opacity: 0, y: 8 }} animate={{ opacity: 1, y: 0 }} transition={SPRINGS.gentle}>{children}</m.div>`);
  `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/template.md:47` ("`template.js`
  renders between `layout.js` and `error.js`. It wraps `error.js`, `loading.js`, `not-found.js`, and
  `page.js`"); `src/components/common/motion-features.tsx:37-40` (`LazyMotion features={loadDomMax}`, the
  feature bundle in its own async chunk); `src/app/layout.tsx:90-107` (every page renders under that one
  `MotionFeatures`); the loading rule this defeats: `docs/spec/DESIGN-SYSTEM.md:461-466` ("every async route
  ships a loading state ... The title is what says where the click went, from the first frame").
- Taxonomy: 6b (a client wrapper high in the tree gating everything beneath it; Suspense fallback that cannot
  show), 6k (a chunk failing mid-load), 6j (first paint at 2,000 members on Indian mobile networks)
- Expected: the design system's loading rule: a hard load of any signed-in route paints its shell and its
  warm-shimmer skeleton from the first streamed frame, then the page. The template's own header says it is
  "Hydration-safe: server and client both render the initial frame, then the client animates."
- Actual: the server renders the template's `initial` into the HTML (fact 4), so everything under the (main)
  layout's shell (the page, its `loading.tsx` skeleton and the `(main)/error.tsx` apology, all of which the
  template wraps per the doc quoted above) arrives as `style="opacity:0;transform:translateY(8px)"`. On every
  HARD load (opening the app, a refresh, a link from an email, WhatsApp or the PWA icon) the member sees the
  sidebar or the green phone bar and an empty page area until (1) the route's JavaScript has downloaded and
  hydrated, (2) the `domMax` chunk has downloaded, and (3) the spring has run. The skeletons rebuilt on
  2026-09-21 at the owner's word ("make them perfect on all pages", DESIGN-SYSTEM §7) are streamed and never
  seen on exactly the loads they exist for; the member watches blank paper instead. Since 19be10b0 (links stop
  prefetching) every soft navigation also waits on a server render, but those are not blank: motion is loaded,
  so the skeleton fades in with the 8px rise. If the feature chunk fails (a flaky mobile connection at that
  moment, an extension, a proxy), `LazyMotion`'s unhandled rejection means no `m.*` element ever leaves
  `initial`, and since this one wraps every page, the whole signed-in app shows a sidebar over nothing, with no
  error and no report, until a reload. T8b's erratum to T8b-07 lists `FadeRise` and 73 other
  `initial={{ opacity: 0 }}` sites as the regions that go blank; this is the one that makes it total.
- Why: a template is the right place for a per-navigation entrance (it remounts on every navigation), but it
  also renders on the first request, where there is nothing to transition from.
- Proof: read-only, no sign-in: `curl -s http://localhost:3000/login | grep -o 'style="[^"]*opacity:0[^"]*"'`
  shows the mechanism on a public page (done 2026-09-27 and again 2026-10-23). Signed in (orchestrator, test
  account): view-source of `/feed` and find the wrapper `div.flex.min-h-0.flex-1.flex-col` carrying `opacity:0`;
  then in chrome-devtools block the `motion-features-max` chunk (network request blocking) and load `/feed`: the
  sidebar paints, the page never does. Throttle to "Slow 4G" with the cache disabled to see how long the
