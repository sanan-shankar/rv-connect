## 0. The connection arithmetic (the headline)

**Short answer.** At 2,000 members the database connection budget is NOT the first thing that
breaks. In steady state and in plausible spikes the pool of 5 per Fluid instance runs at a few
per cent utilisation, because production (Vercel bom1 = AWS ap-south-1, the database's own region)
holds a pooled connection for ~1-3 ms per statement. What breaks first is the free plans' monthly
allowances, reached by ordinary growth: (1) Vercel Hobby's 1,000,000 invocations and 4 Active-CPU
hours, spent chiefly by the presence beacon and a proxy that runs on every request (L5-01, at
~450-800 weekly-active members), and (2) Supabase Free's 5 GB of pooler egress, already about half
spent today by the nightly backup and the pages that stream the whole community (L5-07, at
~500-900 members) — either pauses or restricts the whole site. Then (3) the 500 MB database
line, which a sign-in bot can reach in about a day because every refused attempt writes a row
(L5-02) and ordinary growth reaches in one to two years (L5-08); and (4) CPU on the shared
Nano/Micro Postgres once whole-table aggregates meet a year of data (L5-03) — which is what turns
a burst into `connectionTimeoutMillis: 5000` failures and O-03's sign-out. The laptop's O-03 evidence
(one member exhausting the pool, `findings.md`) is real as a mechanism but ~100x overstated as
a frequency: London -> Mumbai is ~200 ms per statement and ~1 s per new connection, bom1 -> Mumbai
is ~1 ms.

### 0.5 Connections needed (Little's law: busy connections = statements/s x hold time)

| Scenario | Statements/s | Busy connections | vs pool of 5 / Supavisor 15 | Verdict |
|---|---|---|---|---|
| 2k steady peak, today's data size | ~3.5 req/s x ~15 = ~50/s | 50 x 2 ms = **0.1** | 2% / <1% | ample |
| 2k blast (5 hard loads/s), today's data | 5 x 32 = 160/s | 160 x 2 ms = **0.3** | 6% / 2% | ample |
| 2k blast, **2k data size** (aggregates ~100 ms, ~2 per load) | 160/s | 0.3 + 5 x 2 x 0.1 s = **1.3** busy; DB CPU ~1 CPU-s per s | 26% of one instance's pool; ~50% of a 2-vCPU shared DB spent on aggregates | degraded, not failing |
| 100 simultaneous hard loads (the charter's upper case), 2k data size | ~3,200 statements at once | ~200 aggregate statements x ~0.1 CPU-s = **~20 CPU-s of work on 2 vCPU** | the pool is not the limit; the CPU is | statements take seconds -> queued checkouts exceed 5 s -> `timeout exceeded when trying to connect` -> O-03 sign-outs and T8b-02's error screens |

**Where `connectionTimeoutMillis: 5000` starts failing requests.** A checkout fails when the work
queued ahead of it on the same instance exceeds 5 connections x 5 s = 25 connection-seconds. At
~2 ms per statement that is ~12,500 queued statements — unreachable at 2,000 members. At the
2k-data-size cost of a feed hard load (~28 cheap statements + ~2 aggregate statements ~= 160 ms of
connection time) it is ~156 simultaneous feed loads on one instance; once the shared CPU saturates
and the aggregates stretch to ~0.5-1 s it is **~30-40 simultaneous feed/profile/Edition loads**,
which a 2,000-member blast can produce. Independently of load, the NEW-connection half of the same
timer fires whenever Supavisor is slow to accept a connection (third-party evidence: supabase#49991,
12-93 s accept stalls on another project; supabase discussion #40671, zombie client slots under
Vercel Fluid, fixed by supavisor#783) — and with `idleTimeoutMillis` at 10 s, most requests on a
quiet site open fresh connections (L5-04).

**What the member sees then** (not re-derived; cited): the session read loses -> null session ->
`/login?next=` with a valid cookie (O-03 / T5-17); a layout query loses -> the ROOT error page with
no shell (T8b-02); the page's own query loses -> `(main)/error.tsx`; an action's `auth()` loses ->
"Not authenticated" / "Check your connection" (T5-06, O-04); an interactive transaction gives up at
**2 s**, not 5 s (L5-05); and on the money path, `confirmContribution`'s own `auth()` losing the
race returns a red "Not authenticated" AFTER the payment has moved and re-enables the Contribute
button, so a second charge is one click away (T8a-12, Medium — the one pool-timeout consequence
that costs a member real money). `prisma.ts`'s "fast, honest error" is honest only in the page
that throws; the commonest face is the sign-in form.

Ranked by what a `max: 5` checkout timeout breaks at 2,000 members: (1) O-03/T5-17 sign-out
mid-form (every page, most likely); (2) T8a-12 possible double charge (rare, money);
(3) T8b-02 root error page with no shell (layout queries); (4) L5-05 transaction paths failing at
2 s (answer saves, Catch-up creation, the clock's transitions); (5) silent loss of telemetry
writes (`recordPageView`, `touchLastSeen`, `recordLoginAttempt` all swallow in production).

(Timestamps in this report were formatted inside SQL with `to_char` over UTC `timestamp` values,
so the orchestrator's note that node-pg prints `timestamp without time zone` columns an hour early
on this BST machine does not apply to them; rates and gaps are unaffected either way.)

**The prisma.ts comment's model is stale.** "5 x ~40 concurrent instances stays under [Supavisor's
200]" is pre-Fluid reasoning; under Fluid the instance count at 2,000 members is single digits per
function, so the 200-client cap is not the risk. What IS stale-and-risky: the pool never closes
idle clients before the instance suspends (no `attachDatabasePool`), so suspended instances keep
client slots open (Vercel KB: "Idle connection timeouts don't run while suspended") — L5-04.

## 6. k6 load-test plan (a PREVIEW deployment only — never the shared production database)

Designing it is in scope; running it is not, and running it carelessly would itself hit L5-01,
L5-02 and L5-07. Every guard below exists because of one of those findings.

### 6.1 The environment (all four are hard requirements)
1. **A separate Supabase project in a separate organisation**, same tier as production (Free/Nano,
   `ap-south-1`). Supabase applies Free-plan restrictions "to all projects of the restricted
   organization" (billing FAQ) — a load test that blows the test project's 5 GB egress inside
   the owner's org could restrict PRODUCTION. Apply the schema with the repo's own path
   (`prisma/migrations-manual/*` via `scripts/dev/run-sql.mjs --env .env.loadtest`, plus the nine
   hand-made indexes), enable `pg_stat_statements`.
2. **A Vercel preview in `bom1`** built from the audited commit, with Preview-scoped env vars
   pointing at that project (`DATABASE_URL` on 6543 with the same `max: 5` pool — the thing under
   test), `PRESENCE_IN_DEV=1` (else `statsWritesEnabled()` skips every presence write on a
   preview, `stats-exclusion.ts:46-48`, and the test undercounts the write load), NO Upstash
   credentials (the preview is `NODE_ENV=production`, so it would share production's `rl:p:`
   buckets AND its 500,000-command month; with no keys every limit is open, which also keeps
   k6's single IP from being metered), NO `RESEND_API_KEY`, NO PostHog key, and the Sentry DSN

   and breakpoint only if the plan decision needs them. Record the invocation count per scenario: it IS the
   L5-01 measurement.

## Findings

### L5-01 — On the way to 2,000 members the Vercel Hobby plan runs out before the database does: the presence beacon plus a proxy that runs on every request put the site past 1,000,000 invocations a month, and Hobby then stops serving functions for up to 30 days
- Severity: Critical (hard-down for everyone, for up to 30 days, reached by ordinary use)
- Confidence: likely (every per-request multiplier is read from source; the per-member rates are live telemetry; the unknowns are prefetch and PostHog batch counts, and the owner's Vercel Usage page settles them in one look — see Proof. What would change my mind: a current "Function Invocations + Routing Middleware" total under ~110,000 for the last 30 days at today's ~220 members)
- Where:
  - `src/components/analytics/presence-beacon.tsx:30` (`const BEAT_MS = 60_000;`), `:56-60` (`ping("view", pathname)` on every pathname change), `:68-70` (`setInterval(() => { if (active()) ping("beat", path.current); }, BEAT_MS)`), `:74-77` (a beat on every tab hide) — one POST per navigation and one per active minute per open tab
  - `src/app/api/presence/route.ts:29-62` — each POST is a function invocation (auth read + an `after()` UPDATE)
  - `src/proxy.ts:418-422` — `matcher: ["/((?!_next/static|_next/image|favicon.ico|icon.svg|apple-icon.png|manifest.webmanifest|robots.txt|sitemap.xml|images/|uploads/).*)"]`: the proxy runs for `/api/presence`, every `/ingest/*` PostHog batch (`:128`), every RSC request, prefetch and server action. Vercel: "Routing Middleware is priced using the fluid compute model" and Next 16's proxy "runs on Node.js only" — each matched request is an invocation of its own, on top of the function it forwards to
  - `src/components/analytics/posthog-client.ts:91-103` (`autocapture: true`, `capture_pageview: "history_change"`, `capture_pageleave: true`) — batched to `/ingest`, i.e. through the proxy
  - no `prefetch={...}` anywhere in `src/` outside lab: every `<Link>` uses Next's default production prefetch
- Taxonomy: 6j (third-party quotas under load; identical cross-user work), 6f (Vercel limits against exact numbers)
- Expected: headroom to 2,000 members (the owner's brief); the project's own comments reason about the database's 500 MB and the pooler's 200 clients but nowhere about the plan's monthly allowances.
- Actual (arithmetic from live telemetry, 7 days to 2026-09-24: 166 visitors, 610 visits, 5,238 views, 5,804 active minutes):

  | Stream | Requests / week today | Why |
  |---|---|---|
  | presence POSTs | ~11,650 (5,238 view pings + <=5,804 beats + ~610 hide pings) | beacon cadence above |
  | page requests (hard or soft navigation) | ~5,238 | every `(main)` route is dynamic |
  | server actions | ~2,600-7,900 (0.5-1.5 per view: `loadPosts`, `markFeedSeen`, threads, hearts, the letters autosave every 2.5 s of idle) | T1-06, `post-feed.tsx:89,121,149` |
  | RSC prefetches | ~2,600-10,500 (0.5-2 per view; production-only, so never seen in dev) | default `<Link>` prefetch |
  | PostHog `/ingest` batches | ~5,200-15,700 (1-3 per view) | proxy only |

  | **function invocations** (all but `/ingest`) | ~22,000-35,000 | |

  Hobby's allowance is 1,000,000 invocations a month (= ~231,000 a week), so it runs out at **~450-800 weekly-active members**: ~1,100-2,000 members at a 40% weekly-active rate, ~600-1,050 at this week's 75%. The presence beacon alone is ~100,000 invocations a month today (each POST counts twice, proxy + function) and **~480,000-900,000 a month at 2,000 members** — half to nearly all of the allowance spent on statistics. Active CPU is the second ceiling: 4 CPU-hours = 14,400 CPU-seconds, so at 1.0-3.4 M invocations the average must stay under ~4-14 ms of CPU per invocation, while a server render of `/feed` (React RSC render + Prisma's WASM query compiler + serialisation) plausibly costs tens of ms. Hobby's rule when either is exceeded: "you will have to wait until 30 days have passed before you can use the feature again" — functions stop, which for this app is every page.
- Why: every navigation and every minute of reading is a round trip to a function, and the proxy doubles it; nothing budgets invocations. The comments that do the capacity maths (`prisma.ts:27-30`, `retention.ts:58-77`) reason about the database only.
- Proof: read-only, one look at Vercel -> Project -> Usage for the last 30 days: Function Invocations, Routing Middleware invocations (or "Middleware"), Active CPU. Multiply by 2,000 / (members at the start of the window) and compare with 1,000,000 and 4 h. On a preview deployment (never production), the k6 plan in section 6 counts invocations per scripted visit directly.
- Fix direction: (1) take `/api/presence` out of the proxy matcher (the route authenticates itself), and serve PostHog's `/ingest` from somewhere that is not the proxy WITHOUT reopening C-198 (the session cookie is host-only, so a first-party ingest subdomain or a Cloudflare Worker on the owned domain never receives it); (2) change the presence cadence: a beat every 5 minutes, or one `navigator.sendBeacon` on `pagehide` carrying the visit's minutes (owner decision: the analytics room's minute-level visit length is what is being bought with ~half the plan); (3) measure prefetch on a preview and turn it off (`prefetch={false}`) on the high-count link lists if it is a real share; (4) put a monthly check of the Usage page in OPERATIONS.md and decide the plan before launch — Pro bills overage instead of pausing.
- Gate: a unit test pinning that the proxy matcher excludes `/api/presence` and `/ingest`; a test pinning `BEAT_MS` at the agreed value; the section-6 k6 run reporting invocations per visit.
- Known-related: C-198 (why `/ingest` goes through the proxy today — must stay fixed), T1-06 / T8b-12 (actions that re-render the whole shell), L8 (the platform-limits table; this finding is the 2,000-member projection of it).

### L5-02 — A sign-in bot that the rate limiter "stops" still writes one database row per attempt and spends Upstash commands per attempt: a single machine can fill the Free plan's 500 MB (read-only database for everyone) in about a day, and exhaust the month's Upstash quota (every rate limit then fails open) in hours
- Severity: Critical (read-only database = every write in the app fails for every member until the owner intervenes by hand; the retention sweep cannot rescue it because a DELETE is a write)
- Confidence: certain on the mechanism and the per-attempt costs (quoted below); whether it happens needs an attacker or a persistent credential-stuffing bot — the NextAuth credentials callback is a well-known path, and this is exactly the traffic the limiter was built for
- Where:
  - `src/lib/auth.ts:104-110` — `const [ipOk, acctOk] = await Promise.all([hasBudget("login-ip", ip), hasBudget("login-account", acctKey)]); if (!ipOk || !acctOk) { recordLoginAttempt({ email, ok: false, reason: "rate-limited" }); throw new RateLimitedLogin(); }` — two Upstash commands and one row BEFORE the bot check, even for a caller already over the limit
  - `src/lib/auth.ts:167-180` — no Turnstile token: `hasBudget("login-unverified")` + `consume("login-unverified")` (two more commands) and, once the 5/hour allowance is spent, `recordLoginAttempt({ ..., reason: "bot-check", detail })`
  - `src/lib/login-attempt.ts:38-60,91` — `prisma.loginAttempt.create({ data: { email: input.email.trim().toLowerCase().slice(0, 200), ... } })`, no throttle, no dedupe, attacker-chosen email up to 200 characters
  - `src/lib/retention.ts:53,122-123` — `securityLogs: 365`, applied to `loginAttempts`: the rows stay a year
  - `src/lib/rate-limit.ts:286-297` (`hasBudget` -> `getRemaining` = one EVALSHA) and `:15-20` (fail OPEN on any Upstash error); `@upstash/ratelimit` v2.0.8 with `analytics` off (`dist/index.js:776`), so exactly one command per call
  - `prisma/schema.prisma` `LoginAttempt`: indexes `createdAt` + pkey (live `pg_indexes`)
- Taxonomy: 6j (unbounded tables vs the retention sweep; third-party quotas under load), 6k (Upstash quota exhausted; Sentry during an error storm)
- Expected: the header of `rate-limit.ts` — the limiter is what makes abuse cheap for the site; `login-attempt.ts` — "ADDITIVE ONLY ... never blocks"; the privacy/retention story — a security log, not an amplifier.
- Actual: every refused attempt costs the site one INSERT and 2-4 Upstash commands, whatever the limiter decided.
  - Database: 382 MB of headroom (500 MB - 118 MB, live) / ~450-500 B per row (LoginAttempt measures 504 B/row including its two indexes today; a 200-character email is ~+170 B) = **~760,000-850,000 attempts**: ~9-10 days at 1 request/s, **~21-24 hours at 10/s**, ~4-5 hours at 50/s. Supabase then puts the project in read-only mode ("cannot execute INSERT in a read-only transaction"): no post, answer, heart, presence row, `lastSeenAt`, token, sign-up or password reset can be written; reads keep working, so the site looks up and every action fails with a generic sentence. Recovery is manual (override the read-only flag, delete, VACUUM).
