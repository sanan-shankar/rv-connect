## Table 2 — the confirmation-mail state machine, as the code draws it

Row states (`OutboundEmail.status`): `queued` → `sending` (claim, `email-queue.ts:191-194`) → `sent`
(`:339-352`) | back to `queued` (transient, `:276-293`; attempt failure, `:297-306`; stale reclaim after
2 min, `:779-782`) | `failed` (attempts 4 or deferrals 10, a non-retryable skip, `:326-330`). After
`sent`, only the webhook moves it: `email.bounced` → `failed` + `bouncedAt`; `email.complained` →
`failed` + `complainedAt`; `email.delivered` → `deliveredAt`; `email.delivery_delayed` → `lastError`;
`email.failed`/`email.suppressed` ignored (L11-05). Admin Retry → `queued` with counters zeroed (`to`,
`sentAt`, `bouncedAt`, `providerId` untouched).

What the member sees is a function of (latest verify row of ANY address, the account's current address,
budget, sendability) — `verificationMailState` (`:985-1082`) read by the layout (`layout.tsx:96-104,
180-206`) — and the gate is a function of (every verify row to the CURRENT address) —
`confirmationStillWaiting` (`mail-policy.ts:357-365`) via the session.

| Latest verify row | Banner (`layout.tsx`) | Control | Gate (`emailGateOpen`) | Transitions out | Notes |
|---|---|---|---|---|---|
| none | "Confirm your email." | Send me the link | shut (no row, nothing waiting) | button → queued | reachable when signup's enqueue threw, or 180 d after the last row (retention) |
| queued, due, budget left | "imminent" (send scheduled in `after()`) | none | open (nothing sent to this address) | → sending → sent | C4-03 (move mid-claim) |
| queued, budget spent | "queued": open → "We'll send … Everything is open"; shut → "We have hit today's email limit" | none | open unless an earlier row to this address was sent | → sent at refill | L3-01 (label), **C5-04** (the "limit" sentence also covers a provider backoff) |
| queued, `nextAttemptAt` > 10 min away | "queued" with the retry time | none | as above | → sent | **C5-04** |
| sending | "imminent" | none | open if never sent | → sent / reclaimed | L11-03 (accepted-but-unrecorded resend) |
| sent | "We sent a link to <current address>" | Send it again | shut | resend → new queued row; webhook → failed | T5-13 (resend refused-and-swallowed), C4-02 (after a move) |
| failed + bouncedAt | "We couldn't deliver … <current address> didn't accept it" | Use another email (+ retry in the dialog when MailboxFull) | shut (sentAt set) | move → re-address queued rows + enqueue | C4-02 (address-blind), L11-05 (suppressed resend flips back to "sent") |
| failed, no bouncedAt (complained, attempts/deferrals spent, undeliverable TLD) | mapped to "none": "Confirm your email." | Send me the link | shut | button → queued | complained → resend into Resend's suppression (L11-05) |
| queued, production has no `RESEND_API_KEY` (`queueIsSendable` false) | "imminent" for ever | none | open for ever | — | T5-08 |

Confirmation itself: `confirmEmailToken` (token's `sentTo` must equal the current address, else
"stale"), `resetPassword` (sets `emailVerified` as a side effect). **Neither touches the member's
other queued verify rows** — **C5-05**.

## Findings

### C5-01 — Anyone who has seen one member's photograph can make Vercel transform it a million times by changing a query string, and at the owner's spend cap that pauses the whole site: the C-134 allowlist stops other hosts, not other URLs
- Severity: Medium (a deliberate attacker; the consequence is L8-04's — production answers 503 until the owner resumes it by hand — reached with roughly a thirteenth of the requests, through a door the code believes is closed)
- Confidence: certain on the matcher (run below, pure function, no network); likely on Vercel's side (its optimizer honours the same `remotePatterns` and caches per source URL, width, quality and format; a distinct `url` is a distinct cache entry and so a billed transformation). What would change my mind: Vercel normalising the source URL's query string before keying its cache, which nothing in its documentation says.
- Where:
  - `next.config.ts:382-386` — `remotePatterns: imageHosts.map((hostname) => ({ protocol: "https" as const, hostname }))`: no `pathname`, no `search`
  - `node_modules/next/dist/shared/lib/match-remote-pattern.js:46-50` — `if (pattern.search !== undefined) { if (pattern.search !== url.search) return false; }`: an absent `search` admits ANY query string; `node_modules/next/dist/server/config.js:563-571` — Next 16 defaults LOCAL patterns to `search: ''` ("All paths are not allowed for a search query by default") and does no such thing for remote ones
  - `node_modules/next/dist/shared/lib/image-config.js` — 17 permitted widths (8 `imageSizes` + the 9 `deviceSizes` at `next.config.ts:394`), `qualities: [75]`, `formats: ['image/webp']`
  - `src/proxy.ts:423` — `/_next/image` is outside the proxy matcher, so nothing of ours sees these requests
  - the comments that believe it is closed: `next.config.ts:18-35` ("The endpoint is deliberately public ... so the allowlist is the only thing standing there"; "once per unique URL, signed out, in a loop" — the attack it describes is still open, on our own host), `:383-385` ("The optimizer will fetch and transform anything matching this list ... so it is the exact hosts and nothing more"), `src/lib/image-cdn.ts:50-53` ("No new attack surface: /_next/image only fetches hosts listed in next.config.ts remotePatterns")
  - where a stranger gets a URL: any member's page (Stage 0 reads the feed), the Keeper's avatar on the public `/catchups/join/<token>` page (`catchups/join/[token]/page.tsx:124`, `BirdAvatar` → `next/image` on `photoUrl`)
- Taxonomy: 6f/6j (third-party metering under abuse), 6g (the image host), comment-that-lies, C-134 incomplete
- Expected: C-134's fix (`docs/audit-fix/2026-08-22-bug-audit-2/fix-ledger.md:92`) — the optimizer is not an open amplifier; each stored image is transformed once per width.
- Actual: `/_next/image?url=https://images.rishivalley.space/<any real key>?n=1&w=3840&q=75`, then `?n=2`, `?n=3` ... is a fresh source URL every time: R2 ignores the query and serves the same bytes, Vercel finds nothing in its cache, fetches, transforms and writes a new entry. On Pro (L8 §0.1: $0.0527 per 1,000 transformations and $4.40 per million cache writes in bom1, plus the CDN request) one request costs ~$0.00006, so the ~$67 left of the $20 credit plus the $50 On-Demand Budget is ~1.1 million requests: ~3 hours at 100 a second, ~15 hours at 20 a second, from one machine, with no account. Then Spend Management pauses production for every project on the team (503 `DEPLOYMENT_PAUSED`) until the owner resumes it by hand (L8-04's mechanics). L8-04 priced the same outage at ~15 million page renders; this door is ~13 times cheaper for the attacker, and unlike a page render it is not something a WAF rule on `/`, `/login` and `/signup` (L8-04's fix list) would cover.
- Why: C-134 was framed as "which HOSTS may the optimizer fetch", and Next's `remotePatterns` has a second axis, the query string, whose default for remote patterns is "anything". Next itself closed that axis by default for local images in v16 and left remote patterns to the config.
- Proof: done, pure (no network, no route): `node -e` over `next/dist/shared/lib/match-remote-pattern.js`'s `hasRemoteMatch` with this config's patterns → `.../u/a.webp` true, `.../u/a.webp?v=1` true, `?v=2` true, `https://evil.example.com/a.webp` false; the same patterns with `search: ""` → `?v=1` false and the bare URL still true. Read-only safety check for the fix: no stored image URL carries a query string (`Image.url`, `Photo.url/thumbUrl/screenUrl`, `LinkPreview.thumbUrl`, `User.photoUrl`: 0 rows with `?`). A live demonstration would spend the owner's money; argue-only past the matcher (a single local `curl` of the optimizer with a query string was refused by this session's permission layer and is not needed).
- Fix direction: add `search: ""` to every remote pattern (and a `pathname` per prefix the app actually serves through the optimizer — avatars, post images, Catch-up pictures — so the 40-megapixel Collection originals, which are never rendered through `next/image`, cannot be requested at w=3840); add `/_next/image` to the WAF rate-limit rule L8-04 recommends; correct the three comments.
- Gate: extend L9-01's suggested evaluated-config test (load `next.config.ts`, assert over `images.remotePatterns`) with "every remote pattern pins `search` to the empty string".
- Known-related: C-134 (host half, fixed); L8-04 (the budget/pause mechanics; this is a cheaper door into it); L5-11 (Hobby-era 402 consequence, moot on Pro per L8); L9-01 (the C-134 pin cannot see this axis either).

### C5-02 — One person with one browser and the contact address printed on /privacy can spend the day's 95 emails on password resets every day, so nobody else's reset or confirmation goes out until 05:30 IST; M3's per-IP meter turned "minutes" into "hours", not into "never"
- Severity: Medium (a deliberate griefer, but cheap and repeatable daily; the consequence is every locked-out member waiting up to a day for a reset, every security notice delayed, every confirmation delayed — and a few hundred reset mails a week landing in the targeted inboxes, which is the traffic that earns a young sending domain spam complaints)
- Confidence: certain on the mechanism and the arithmetic (every number below is a constant in the code); possible on someone doing it.
- Where:
  - `src/components/auth/email-actions.ts:238-249` — the guard and its premise: "The per-IP limit is audit M3 — before it, one caller cycling known addresses could burn the whole day's ~95-message mail budget in minutes, taking password recovery down for everyone"; `:281-294` the enqueue
  - `src/lib/rate-limit.ts:76-79` — `reset: { tokens: 5, window: "15 m" }` per IP = 20 an hour, and nothing per day
  - `src/lib/email-queue.ts:435-437` — per ACCOUNT `reset: { max: 4, windowMinutes: 30 }` (8 an hour); `src/lib/auth-tokens.ts:56-59` the same 4/30 m for the mint
  - `src/lib/email-queue.ts:87` (`DAILY_CAP = 95`), `:103` (`RESET_RESERVE = 10`) and `src/lib/mail-policy.ts:46-59` — resets are RESERVED kinds and "may spend the daily budget all the way down"; `:26-34` reset priority 10 ahead of verify 100; `email-queue.ts:839` oldest-first within a priority, so the attacker's resets and a member's real one queue together
  - `src/lib/email-queue.ts:466-494` — the fold only absorbs a request while a reset is WAITING; with budget left each reset is sent within seconds, so the next request makes a new row
  - `src/app/(policies)/privacy/page.tsx:216-217`, `src/app/(policies)/terms/page.tsx:105-106` — a contact address that is a live account with a password (read-only: 1 row, `password IS NOT NULL`, not blocked); L10-05 says it is the test account and an admin
- Taxonomy: 6j (third-party quota under load — Resend's 100/day), 6k, comment-that-lies (M3's premise)
- Expected: M3's promise — one caller cannot take password recovery down for everyone; `email-queue.ts:48-52` — "A password reset must NEVER queue behind a hundred welcome emails".
- Actual: a script (or a person with a real browser, where Turnstile usually passes without a click) asks for a reset of the published address every 7.5 minutes: 8 sends an hour, the whole day's 95 in ~12 hours; with two or three known addresses (C1-06's public repository carries more), the IP meter's 20 an hour binds and the day is gone in ~5 hours from one connection, ~2.5 from two. From then until the next UTC midnight (05:30 IST): every real reset is accepted on screen ("on its way") and sits queued; every confirmation sits queued; password-changed and deletion notices sit queued. At midnight the real backlog goes first (the attacker's own rows fold to one per account while the budget is empty), and the attacker starts again. Repeat daily; the cost is ~95 Turnstile solves a day. The targeted inboxes receive ~95 reset mails a day, each burning the previous link; a recipient who marks them as spam pushes the account toward Resend's complaint threshold (L8 §0.4 quotes "spam under 0.08% ... or a temporary pause in sending"), after which nothing sends for anyone. Side effect on the gates: while the budget is empty, every new signup's confirmation is "still waiting", so `confirmationStillWaiting` keeps their email gate open without any mailbox ever being proven (d7a8041d's owner rule, held open by the attacker rather than by a launch).
- Why: the per-IP meter bounds a RATE; the budget is a DAY. 20 an hour × 24 is five times the budget, and per-account 8 an hour × 12 hours is the whole of it, so neither bound is below the ceiling it protects. The reserve protects resets from confirmations, never from other resets.
- Proof: arithmetic from the constants above (no live call can be made — each one is a real mail). Read-only baseline: sends in the last 30 days peak at 1-2 resets a day (`SELECT date_trunc('day',"sentAt"), kind, count(*) FROM "OutboundEmail" ... GROUP BY 1,2`), so an attack is the whole of the day's traffic. A unit-level pin is possible: with `enqueueMail` stubbed, 96 resets spread over 12 hours for one user and one IP all pass every meter today.
- Fix direction: cap what one ACCOUNT may receive per day (e.g. 3 resets per address per 24 h, enforced in `enqueueMail` on `kind: "reset"` by counting rows since the valley day or rolling 24 h — the per-recipient bound is the one the attacker cannot multiply with IPs); cap resets' share of the day below the whole budget (resets may use the reserve plus N, not everything); and a per-IP daily ceiling on the reset door. Consider not printing a live login address as the policies' contact (a role inbox that is not an account).
- Gate: a `mail-policy`-level pure rule "resets for one address in 24 h ≤ K" with a test, and a test that the reset kinds cannot consume more than `DAILY_CAP - X` in one day.
- Known-related: M3 (audit 1, the meter this outgrows), C-161/L3-01 (natural backlogs; this one is induced), L10-05 (the published address is the admin test account), C1-06 (the public repository's other addresses), L8 §0.4 (Resend's complaint threshold). Not L5-02 (sign-in rows) — no row flood here; the scarce thing is the mail.

### C5-04 — During a Resend outage of about twenty minutes, a member waiting on a resend is told "We have hit today's email limit" on a day with budget to spare
- Severity: Low (the time it names is the real retry time and "nothing you need to do" is right; the reason is false, and it is the exact sentence the queue's header says no path can show)
- Confidence: certain on the path; the trigger is an ordinary provider incident

- Known-related: C-107 (the fix that opened this path), L3-01 (the label's day), T5-08 (the opposite lie, "sent" when nothing can send).

### C5-05 — Confirming by another route leaves the member's queued confirmation in the line: on a backlog day it still goes out, spending a slot someone else is waiting for
- Severity: Low (one wasted slot and a redundant "Confirm your email" per such member, only on days the budget is short; clicking it rewrites the confirmed-at date the admin sees)
- Confidence: certain on the mechanism; how many members hit it on a launch day is unknown
- Where: `src/components/auth/email-actions.ts:193-201` (`confirmEmailToken` writes `emailVerified`), `:376-398` (`resetPassword` writes `emailVerified` "a reset doubles as a confirmation"); neither touches the member's other `OutboundEmail` rows (the only row writers are listed in Coverage); `src/lib/email-queue.ts:818-841` (the drain selects `queued` rows by kind and age, with no look at the account), `:578-621` (`render()` mints a verify token for any `userId`); `:1012-1013` and `layout.tsx:102` (a confirmed member's state is never read again, so nothing self-heals it); `src/app/(main)/admin/people/[id]/page.tsx:119` (the admin's "Confirmed <date>" is `emailVerified`, which `confirmEmailToken` overwrites on every later click)
- Taxonomy: 6i (queue rows outliving the state they were for), 6j (the 95/day budget)
- Expected: `email-queue.ts:96-101` — on a launch day "each of those is a person's link slipping to tomorrow"; the queue spends slots on mail somebody still needs.
- Actual: two ordinary paths. (a) On a budget-spent day a member presses "Send it again" (their first link had gone out), is told "goes out tomorrow", then finds and clicks the first mail; tomorrow the queued row is still sent. (b) A member whose first confirmation is queued behind a backlog forgets their password; the reset jumps the line (priority 10), confirms them, and their confirmation still goes out later. Each costs one of the 85 confirmation slots the backlog is rationing, sends a mail that asks a confirmed member to confirm, and, if clicked, moves `emailVerified` forward to the click.
- Proof: argue-only on live data; a unit-level pin: a `drainEligible`-style predicate that today has no account input at all.
- Fix direction: in `confirmEmailToken`'s and `resetPassword`'s transactions, mark the member's `queued` verify rows done (`status: "failed", lastError: "confirmed by another route"`, or delete them); belt and braces, have `render()` skip a verify row whose user is already confirmed (a non-retryable skip); make `confirmEmailToken` leave an existing `emailVerified` alone.
- Gate: a source pin that both confirmation writers retire queued verify rows in the same transaction.
- Known-related: C-161 (the backlog this wastes slots of), C5-02 (the induced backlog).
