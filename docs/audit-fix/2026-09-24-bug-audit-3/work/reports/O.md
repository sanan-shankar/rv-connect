### O-01 — The letters index renders a draft's "Edited <day> <month>" without a time zone: a nightly hydration error, and a date one day off for drafts edited late in the evening
- Severity: Medium
- Confidence: certain (live: React's hydration-mismatch error in the dev log with "+ 23 Sept / − 24 Sept" at `drafts-strip.tsx:97`; the call has no `timeZone`)
- Where: `src/components/letters/drafts-strip.tsx:97-102` (`new Date(d.updatedAt).toLocaleDateString("en-GB", { day: "numeric", month: "short" })` inside a JSX expression, rendered on the server for `/letters` by `letters/(index)/page.tsx:148` and again on the client); `src/lib/valley-day.test.mjs:109-131` (the sweep meant to catch this: its regex `toLocale(?:Date|Time)String\(([^;]*?)\)\s*[;,)\n]` does not match a call that closes with `})}`, so the gate is green with the bug present — bugs.md #6 even names "the letters index" as a latent instance of this class).
- Taxonomy: 6h dates (server UTC vs members IST) · 6b hydration mismatch · L9 a sweep that pins the instance shape, not the property
- Expected: `formatDisplayDateLong`/`formatDayAndDate` in `utils.ts` carry `timeZone: "Asia/Kolkata"`; every rendered date is a valley date (`valley-day.test.mjs`'s stated purpose).
- Actual: for any draft whose `updatedAt` falls between 18:30 and 24:00 UTC (00:00–05:30 IST — an evening's writing in India), the server (UTC) prints the previous calendar day and the client (IST) prints the next; React logs "Hydration failed … this tree will be regenerated on the client", re-renders the strip, and the member sees a flash; server-rendered HTML (what a crawler, a slow connection or a reader without JS sees) carries the wrong day.
- Why: the option object omits `timeZone`, and the sweep's regex requires the closing paren to be followed by `;`, `,`, `)` or a newline — a JSX `{…}` wrapper ends with `}`.
- Proof: the dev log line (`.next/dev/logs/next-development.log`, "Hydration failed … drafts-strip.tsx:97"). Reproduce: sign in as the throwaway account with a draft saved at 19:00–23:59 UTC, load `/letters` with the browser in IST, read the console.
- Fix direction: `toLocaleDateString("en-GB", { day: "numeric", month: "short", timeZone: "Asia/Kolkata" })` (or the shared `formatDayAndDate`); make the sweep paren-match the call instead of regexing to the next delimiter (the orchestrator's paren-matched sweep found this as the ONLY timezone-less date call in `src/` outside lab/tests — the other nine `toLocaleString` calls format numbers).
- Gate: `valley-day.test.mjs` rewritten to paren-match every `toLocale(Date|Time)String(` call; it fails today on this file.
- Known-related: bugs.md #6 (latent-class note) — this is the live instance.

### O-03 — A five-second wait for a pooled connection during the session read signs the member out: NextAuth turns the throw into "no session" and the main layout bounces them to the sign-in form mid-form
- Severity: High
- Confidence: certain (mechanism from `@auth/core` source; 12 live occurrences in the dev log during the baseline run; T5-17 traced the member-visible path)
- Where: `src/lib/auth.ts:368-393` (the session callback's `prisma.user.findUnique` with no try/catch); `node_modules/@auth/core/lib/actions/session.js:58-62` (catch → `logger.error(new JWTSessionError(e))` → body null); `node_modules/next-auth/lib/index.js:45-49` (the RSC `auth()` reads the body only, so the cookie survives); `src/lib/auth.ts:520-524` (`guardedSession`: null); `src/app/(main)/layout.tsx:26-38` (`redirect("/login?next=…")`); `src/lib/prisma.ts:45-51` (`max: 5`, `connectionTimeoutMillis: 5000`); `src/app/(main)/layout.tsx:83-103` (the four-query `Promise.all` that competes for the same five connections on every page view)
- Taxonomy: 6k (DB slow mid-request) · 6d connection budget under Fluid compute · 6e (unreachable conflated with revoked) · 6j the 2,000-member failure shape
- Expected: a slow database reads as "give it a moment" (the sentence the sign-in door already has for the same condition); the member keeps their page.
- Actual: the page navigates to `/login?next=<path>`; whatever was typed and not yet saved is gone (subject to the letters desk's local belt); the login form shows as if they were signed out although the cookie is valid, and pressing Back or reloading later signs them straight in. Under Vercel's Fluid compute one warm instance serves many concurrent requests against ONE pool of five, so a burst of page views (each needing up to four connections at once) is exactly what produces this; the dev log recorded it 12 times in half an hour under a 25-route crawl.
- Why: the callback's contract has no "could not find out" state; `@auth/core` maps a throw to the same null as an expired token; every consumer treats null as "nobody".
- Proof: `grep -c JWTSessionError .next/dev/logs/next-development.log` → 12 today, each with cause "Connection terminated due to connection timeout". Live, safely: point a local dev server's `DATABASE_URL` at a host that drops packets and load `/feed` with a valid cookie → redirect to `/login?next=/feed`, cookie still present.
- Fix direction: T5-17's (auth side): catch the row read, mark the session `unavailable`, throw a typed `SessionUnavailable` from `guardedSession`, render a retry screen in the (main) layout instead of `redirect("/login")`, map it to a "give it a moment" sentinel in the action gates, and report it (`reportSwallowed`) — the first alarm this failure will ever have raised. L5's (capacity side): the pool arithmetic under Fluid compute; the layout's four-way `Promise.all`.
- Gate: `session-revocation.test.mjs` pin that the row read is inside a try/catch that sets `unavailable` and that `guardedSession` throws on it; a layout test that an unavailable session renders the retry screen and never redirects to `/login`.
- Known-related: T5-17 (the auth-side confirmation and fix), T5-02 (the outage is invisible), T5-06 (the expired-cookie cousin).

### O-05 — Mail queued on a developer's machine is sent for real by production: the local "never mail real people" guard only stops the local process, and production drains the one shared queue
- Severity: Medium

- Taxonomy: 6i (a queue with two producers and one consumer nobody planned for) · 6k · L9 (a comment promising the opposite)
- Expected: the guard's comment — exercising a flow on localhost does not send live mail.
- Actual (live proof, 2026-09-24): the throwaway account "Audit TestBird" <sanan.shankar+audit3@gmail.com> was created through the real /signup on localhost at 01:21:33 UTC. Its `verify` row sat `queued` (the local drain refuses). A dated additive migration with a default of `production` keeps every existing row sendable. Correct the `email.ts` comment either way.
- Gate: a `mail-policy` unit test that `drainEligible` excludes a row whose origin differs from the running environment; a shape pin that `enqueueMail` writes the origin.

### O-06 — A null byte in any search box makes the server throw, the member is told to "check your connection", and the page also claims "No posts match your search"
- Severity: Low (a crafted or pasted character; the consequence is a wrong sentence and a server exception per attempt)
- Confidence: certain (reproduced live on /feed as the throwaway account)
- Where: `src/lib/db-text.ts:49-55` (`escapeLike` clamps and escapes `%`, `_`, `\` but passes U+0000 through); `src/app/(main)/feed/actions.ts:1117` (`prisma.post.findMany` receives it → Postgres `22021 invalid byte sequence for encoding "UTF8": 0x00` → `PrismaClientKnownRequestError`); `src/lib/call-action.ts:43-58` (the rejection becomes `ACTION_FAILED`); the feed's empty state renders beside it.
- Taxonomy: 6h (unicode-hostile input: NUL) · 6a (an error path that paints a success state) · 6j (each attempt is a server exception → a Sentry event, T5-10's quota class)
- Expected: a search for a string that contains an unprintable character finds nothing, quietly.
- Actual (live): `/feed?q=a%00b` → the action POST answers 500 twice, the toast reads "That did not go through. Check your connection and try again.", and the page body reads 'Showing posts for "ab" — No posts match your search.' The NUL is invisible in the heading. Every search that reaches Postgres with the byte shares the path, confirmed live the same minute: `/directory?q=a%00b` → `prisma.user.count()` 22021; `/collection?q=a%00b` → `prisma.photo.findMany()` 22021; `/api/places/search?q=Ban%00g` → `prisma.$queryRaw()` 22021 and a bare HTTP 500 to the city picker. Four surfaces, one missing strip.
- Fix direction: strip C0 controls (at least U+0000) in `escapeLike` — the one door every search passes — and in the shared text validators for stored fields (L6 owns the wider sweep: Postgres rejects `\0` in every `text` column, so any write path that stores member text is exposed the same way); have the feed's empty state distinguish "the search failed" from "nothing matched".
- Gate: `db-text.test.mjs` case: `escapeLike("a\u0000b")` contains no U+0000.
- Known-related: none.

### O-07 — The app's database connection is not encrypted: `pg` is given no `ssl` and the connection string asks for none, so every query and every row crosses the network in plaintext
- Severity: High (the whole member database — names, emails, phones, addresses, bcrypt hashes in auth reads, private letters and drafts — crosses the network unencrypted; certain for every connection made from a developer machine, which reaches the PRODUCTION database from home networks and Wi-Fi; production's own leg depends on one Vercel setting)
- Confidence: certain for the local configuration (proved live below); possible for production until the owner reads one env var
- Where: `src/lib/prisma.ts:45-51` (`new PrismaPg({ connectionString, max: 5, connectionTimeoutMillis: 5_000, query_timeout: 20_000 })` — no `ssl`); `node_modules/pg/lib/connection-parameters.js:23-36,85` (`this.ssl = typeof config.ssl === 'undefined' ? readSSLConfigFromEnvironment() : config.ssl`; with `PGSSLMODE` unset that returns `defaults.ssl`, i.e. `false`); `node_modules/pg-connection-string/index.js:77-78` (only an `sslmode`/`sslcert`/`sslkey`/`sslrootcert` parameter turns SSL on from the URL). The local `DATABASE_URL`'s only query parameter is `pgbouncer`; `DIRECT_URL` has none; `PGSSLMODE` is unset (printed as parameter NAMES only; no secret was displayed). Supabase's pooler accepted the plaintext connection, so "Enforce SSL" is off on the project.
- Taxonomy: 6d (Prisma + pooler configuration) · 6k (the network between the app and the one database) · security-adjacent (reported because it is config the audit read, not because a security audit was re-run)
- Expected: a connection to a database holding real members' personal data is TLS-encrypted and verifies the server (`sslmode=verify-full` with Supabase's CA, or at minimum `require`), and the database refuses anything else.
- Actual (live, 2026-09-24 09:31 BST, read-only): `new pg.Client({ connectionString: process.env.DATABASE_URL })` — the app's own configuration — connected to the Supabase transaction pooler, ran `select 1`, and its socket was a plain `net.Socket` with `encrypted: false`. Every local dev server, every QA script (`run-sql.mjs`, the probes, the visual suite's server), every agent session and `prisma studio` therefore sends queries and receives rows — member PII included — in cleartext from the owner's network to Mumbai. Authentication is SCRAM, so the database password itself is not sent in the clear, but everything after the handshake is. Production uses the same code; whether its connection is encrypted depends only on whether the `DATABASE_URL` in Vercel carries an `sslmode` parameter (the Supabase dashboard's "Transaction pooler" string does not add one by default).
- Why: `pg` defaults to no TLS unless told otherwise, and the connection strings were pasted from Supabase without an `sslmode`; nothing in the code sets `ssl`.
- Proof: the live check above (read-only, one `select 1`). Production: the owner opens Vercel → Project → Settings → Environment Variables → `DATABASE_URL` and looks for `sslmode=` (do not paste the value anywhere).
- Fix direction: set TLS in code so no environment can forget it: `ssl: { rejectUnauthorized: true, ca: <Supabase's root certificate, committed to the repo> }` in `prisma.ts` (and the same for `scripts/dev/run-sql.mjs` and the backup's `pg_dump` via `sslmode=verify-full`); verify from a dev server and a preview deploy; THEN turn on Supabase → Database → Settings → "Enforce SSL on incoming connections" so a client that forgets is refused rather than served in plaintext. Order matters: enforcing first takes the site down.
- Gate: a unit test that `prisma.ts`'s pool config sets `ssl` with `rejectUnauthorized: true`; optionally a check in `npm run check` that a live `select 1` through the app's config reports an encrypted socket (skipped in CI where no database is reachable).
- Known-related: routed as a lead by L5 (`prisma.ts:45-51`). Not in the dedup baseline; the 2026-08-20 security overhaul's tracker was not re-read line by line for it — the fix session should check `docs/security` for a prior decision before acting.
