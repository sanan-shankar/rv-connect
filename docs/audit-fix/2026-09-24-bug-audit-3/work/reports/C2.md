### C2-01 — When R2 stalls instead of erroring, deleting a post, editing a letter, changing an avatar or removing a photograph spins for minutes and then reports a failure for a change that has already been saved: the storage client is the one outbound dependency in the app with no deadline
- Severity: Low (with teeth: a member-facing false failure on a committed change, and minutes-long spinners across every write that touches storage, for the length of an R2 brownout. No data loss; the database side is already committed and the purge worklist retries the bytes)
- Confidence: certain on the configuration (executed: the client built exactly as `storage.ts` builds it reports no connection, request or socket timeout); likely on the member-facing sequence (it needs R2 to accept and then not answer, a brownout shape rather than a clean 5xx; how long R2's own edge holds such a request before answering is Cloudflare's, not measured here, and the SDK's three attempts multiply it). What would change my mind: an `AWS_DEFAULTS_MODE` set in the Vercel environment (nothing in the repo sets one; `grep -rn defaultsMode src scripts .github vercel.json next.config.ts` is empty), or a per-command `abortSignal` (none is passed anywhere in `storage.ts`).
- Where:
  - `src/lib/storage.ts:37-49` — `_client = new S3Client({ region: "auto", endpoint: ..., credentials: {...} })`: no `requestHandler` options, no `maxAttempts`, no `abortSignal` on any `send()` (`:116-147` putImage, `:201-232` copyObject, `:234-256` readObjectHead, `:264-282` getImageBuffer, `:284-314` headObjectSize, `:316-346` delImageByKey).
  - The SDK's defaults at HEAD: `node_modules/@smithy/core/dist-cjs/submodules/config/index.js:695` (`default: "legacy"`), `node_modules/@smithy/core/dist-cjs/submodules/client/index.js:832-856` (`loadConfigsForDefaultMode` returns `{}` for legacy: no `connectionTimeout`), `node_modules/@smithy/node-http-handler/dist-cjs/index.js:208` (`DEFAULT_REQUEST_TIMEOUT = 0`), `:80-99` (even a configured `requestTimeout` only logs a WARN unless `throwOnRequestTimeout: true`), `:124-138` (socket timeout 0 = none), `:409-425` (one keep-alive agent, `maxSockets: 50`, per instance).
  - Executed offline (no network, dummy credentials), the client constructed as `storage.ts` does: `connectionTimeout= undefined requestTimeout= undefined socketTimeout= undefined throwOnRequestTimeout= undefined`, `maxSockets= 50 keepAlive= true`, `maxAttempts= 3 retryMode= standard`.
  - Request paths that await R2 after their database change has committed: `src/app/(main)/feed/actions.ts:118` (`deletePostWithImages` → `drainPendingImagePurges`, after the delete transaction and the bell cleanup), `:770` (`editPost` drain after the update), `src/app/(main)/collection/actions.ts:1085` (`erasePhoto` drain after the delete transaction), `:1189` (`adminRemovePhoto`), `src/components/settings/actions.ts:136-140,163` (avatar: `swapPhotoUrl` has committed, then `purgeImageUrls` of the old picture; `revalidatePath` and the success return come after it), `src/app/(main)/catchups/actions.ts:1627` (a replaced voice answer), `src/app/(main)/admin/people/actions.ts:431` (merge), `src/lib/account-purge.ts:411,448` (the in-request drain). Paths that await R2 BEFORE writing (fail without a false report, but hang the same): `collection/actions.ts:485-490` (`contributePhotoDirect` HEAD + GET), `settings/actions.ts:124` (avatar PUT), the upload, finalize, audio-finalize and photo-download routes (bounded by their own `maxDuration` 60/60/30/60).
  - Every other outbound call has one: `src/lib/email.ts:205-224` (Resend, 10 s race; its comment is audit M20's reasoning, "a provider that accepts the connection and then says nothing holds the whole page open until the platform kills the function"), `src/lib/razorpay.ts:88` (15 s), `src/lib/turnstile.ts:168` (5 s), `src/lib/wordle.ts:48` (3 s), `src/lib/rate-limit.ts:240` (Upstash 3 s), `src/lib/link-preview.ts:245` (5 s for the whole chain), `src/lib/prisma.ts` (pool connect 5 s, `query_timeout` 20 s).
- Taxonomy: 6k (R2 misbehaving mid-request; the brief names 500/429, this is the stall) · 6a (resource leaks, server half: sockets held with no deadline) · 6f (function duration: the only bound left is `maxDuration`, and the feed, letters, profile and settings pages declare none, so their actions run to the Fluid default) · L4 (a failure reported for work that succeeded)
- Expected: the M20 rule the codebase applies to every other provider: a dependency that accepts and then says nothing costs the member a few seconds and an honest sentence, never the platform's kill. The deletePost comment says "a slow R2 must not hold a transaction open" and the code honours that; it does not stop a slow R2 holding the member.
- Actual: during an R2 brownout that leaves requests open, a member who deletes a post, saves an edited letter that dropped a photograph, changes or removes their avatar, or (as an admin) removes a photograph watches the button's spinner for as long as R2 takes to give up (each attempt waits on R2's edge; the SDK makes three) or until the function is killed. The database change committed before the R2 call, so the post IS gone and the avatar IS changed, but the action then returns nothing or dies, `callAction` draws "Check your connection and try again" (`src/lib/call-action.ts:43-58`), and a retry says the post cannot be found. On the avatar path `revalidatePath` is never reached, so the profile keeps showing the old picture until the next navigation. On the letter desk the autosave IS `editPost`, so an autosave that dropped a photograph hangs in the drain, and Publish, which waits for the in-flight autosave by design (C-175's fix, `composer-rule.test.mjs:188`), waits behind it. On a Fluid instance the stalled sockets stay checked out of the client's one 50-socket agent for the life of each request, so a burst of storage writes during the brownout queues later uploads on the same instance behind them (the handler only warns, `:224-240`).
- Why: the AWS SDK's legacy defaults mode sets no connection, request or socket timeout, and `storage.ts` passes no `requestHandler` options; the three-attempt standard retry then multiplies whatever R2's edge waits. The purge helpers already treat an R2 FAILURE as "queue it and move on" (`image-purge.ts:53-72`), so the only thing missing is the deadline that turns a stall into that failure.
- Proof: executed offline as above (read-only, no network). Live: argue-only, because it needs R2 to stall. An offline unit test can prove the member half: point `R2_*` at a local TCP server that accepts and never answers, call `delImageByKey`, and observe it never settles; the same test with the fix settles in the configured seconds and `purgeImageUrls` queues the URL.
- Fix direction: give the client deadlines once, in `r2()`: `requestHandler: { connectionTimeout: ~3_000, socketTimeout: ~20_000 }` (inactivity, so a large PUT of a 40 MP master that keeps moving is not cut) and, if a total cap is wanted, `requestTimeout` WITH `throwOnRequestTimeout: true` (in this SDK version `requestTimeout` alone only logs); consider `maxAttempts: 2`. Separately, the post-commit drains in member actions (`feed/actions.ts:118,770`, `collection/actions.ts:1085`, the avatar purges) could move into `after()`, since the worklist row already guarantees the retry; then a slow R2 costs the member nothing at all.
- Gate: a source test beside `upload-size-rule.test.mjs` that `storage.ts`'s `S3Client` is constructed with a `connectionTimeout` and a `socketTimeout` (or `requestTimeout` + `throwOnRequestTimeout`), and a sweep that every outbound client in `src/lib` declares a deadline.
- Known-related: L4-03 (an R2 outage has no alarm: that is the error shape, this is the stall shape, and this one also lies to the member); V-T7a's T7a-05 ruling (the admin delete's audit line sits after the in-request drain, "a crash or an R2 hang in the drain window" loses it: the same missing deadline, seen from the audit trail); L11-07 (the sweep's purge budget); T2b-07 (one write a second per key). None names the client configuration.

### C2-02 — The data export promises that "neither end holds it all", but its stream pushes every page as fast as the database answers, so a slow download holds the whole file in the function's memory
- Severity: Low (no teeth at this size: a member's own rows are a few megabytes at most even at 2,000 members; it is the comment that lies, and it is the comment the M48 fix was written to make true)
- Confidence: certain (the stream has a `start` and no `pull`; WHATWG `ReadableStream` queues everything `enqueue` is given)
- Where: `src/app/api/account/export/route.ts:21-31` (the M48 comment: "So neither end holds it all: each table is walked in id order in pages, and each row is written out and dropped"), `:294-318` (`new ReadableStream({ async start(controller) { ... for await (const row of paged(fetchPage)) write(...) } })`, no `pull`, no look at `controller.desiredSize`).
- Taxonomy: 6a (resource use, server half) · 6j (memory per invocation) · L9 (a comment that lies)
- Expected: rows leave memory at the pace the member's connection takes them.
- Actual: `start()` runs the whole walk at database speed and enqueues every chunk; the response pipe reads at network speed, so on a slow phone connection the unsent tail accumulates in the stream's queue until it holds the entire export. The rows themselves are dropped (so the M48 "twice over" is fixed), the encoded text is not.
- Why: a push-mode stream needs a `pull()` (or a check of `controller.desiredSize` before each page) to apply backpressure; this one has neither.
- Proof: offline: wrap the route's stream in a reader that reads one chunk a second and log `controller.desiredSize` after each page; it goes ever more negative.
- Fix direction: move the walk into `pull()` (one page per pull), or `await` a small helper that waits while `controller.desiredSize <= 0`; or correct the comment to say the rows, not the bytes, are bounded.
- Gate: none worth a test at this size; correct the comment if the code stays.
- Known-related: M48 (the fix this comment describes); T6 Verified clean ("the export streams"), which is right about rows.
