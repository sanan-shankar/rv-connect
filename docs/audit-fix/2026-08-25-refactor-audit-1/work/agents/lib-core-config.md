## Summary

This territory is the best-defended part of the codebase I have seen: nearly every file is
comment-heavy (mail-policy at 1.97 comment/code, instrumentation at 1.71, email.ts 1.39), and
nearly every one of those comments carries an audit ID, an incident date, or an owner quote.
Under the brief's own rule (a comment that carries a reason is NOT bloat), the comment mass
here is almost entirely load-bearing, and I say so explicitly in Not-findings so nobody
re-litigates it. The real wins are structural and mostly *outside* the .ts logic: the
TypeScript build step type-checks 87,384 lines of gitignored generated Prisma as root files
(lib-core-config-01); `npm run analyze` has been a verified no-op since the project moved to
Turbopack builds (02); and the demo bar, a component only the demo deployment ever renders,
rides in the first-load client JS of every authenticated production page (03). After those,
it is a modest harvest of dedupe and dead exports: a dead SQLite compatibility branch copied
into three files, a triplicated cron-auth block, one 20-line duplicated doc comment, and a
handful of exports nothing imports. Structural-vs-cheap split: 5 structural, 4 cheap. What
surprised me: the 1,061-line email queue, the obvious "surely this can be an outbox" target,
survives scrutiny completely - every piece of its machinery pins a dated production incident.

## Findings

### lib-core-config-01 - Stop type-checking 87,384 lines of generated Prisma as root files
- **Where**: `tsconfig.json:33-40` (the `include` array, specifically `"**/*.ts"`);
  `src/generated/prisma/**` (49 .ts files, 87,384 lines, 3.8MB, gitignored - verified with
  `git check-ignore`)
- **Phase**: architecture (build-time)
- **Tier**: T2     **Class**: structural     **Decides**: autonomous
- **Evidence**: `tsconfig.json` includes `"**/*.ts"`, which makes every file under
  `src/generated/prisma/` a *root file* of the program. Measured: `find src/generated/prisma
  -name "*.ts" | wc -l` = 49 files; `wc -l` total = 87,384 lines; `du -sh` = 3.8M. The build
  baseline attributes 19.4s of the 45.6s `next build` to the TypeScript step. The directory is
  gitignored and regenerated by `prisma generate` (which runs on `postinstall`). Side effect
  already visible in the tooling: 43 of the 48 madge circular-dependency reports are inside
  this directory (raw/madge-circular.txt), pure noise every future audit has to re-discount.
- **What to do**: add `"src/generated"` to the `exclude` array in tsconfig.json (one line).
  This removes the 49 files as *root* files. Files actually imported by the app
  (`@/generated/prisma/client` from prisma.ts, account-purge.ts, demo/reset/route.ts) are still
  reached and type-checked through import resolution, so correctness does not change; what goes
  away is the checking of generated files nothing imports (browser entry, internal helpers,
  models the barrel re-exports but no root demands eagerly) and their inclusion in the
  program's file graph. Then MEASURE: run `npx tsc --noEmit --extendedDiagnostics` before and
  after (the fixer may run gates; I could not) and record the delta in the fix commit. If the
  delta is small because the barrel pulls everything anyway, the exclude is still correct
  hygiene (root files vs dependencies) and still silences the madge noise; say so honestly.
- **Saving**: 0 lines of code; potentially several seconds of the 19.4s tsc step per build and
  per `npm run check`; kills 43/48 madge cycle reports. The honest range is "0.5s to ~5s" until
  measured - the generated files are .ts (not .d.ts), so `skipLibCheck` never applied to them,
  which is why being a root file vs an import can matter here.
- **Risk & gate**: low. `npm run check` (its tsc gate is the thing being changed - it must
  still pass and still catch a deliberate type error in app code); one `next build` to confirm
  the TypeScript step still passes.
- **Confidence**: high that the exclude is safe and correct; medium on the size of the time
  win (import resolution may pull most of the graph back in regardless).
- **Notes**: I considered recommending Prisma's generator emit elsewhere (node_modules) and
  rejected it: the `@/generated/prisma/client` import path is used in three files and the
  current layout is deliberate (Prisma 7 client generator). Do not touch
  `.next/types/**` in the include - TRAPS documents the stale-validator behaviour there and it
  is Next's own convention. `"**/*.mts"` in include covers scripts/demo/*.mts and is wanted.

### lib-core-config-03 - The demo bar ships in every production member's first-load JS
- **Where**: `src/app/(main)/layout.tsx:16` (static import), `:153` (`{IS_DEMO && <DemoBar/>}`);
  `src/components/demo/demo-bar.tsx` (163 lines, "use client")
- **Phase**: relocate (client-bundle)
- **Tier**: T2     **Class**: structural     **Decides**: autonomous
- **Evidence**: DemoBar is statically imported by the (main) layout and rendered only when
  `IS_DEMO` (a server-side runtime constant, false on the real deployment). A statically
  imported client component is bundled regardless of whether it renders. Confirmed against the
  current build: `grep -rl "You are in a demo" .next/static/chunks/` hits
  `3szri51gnxmii.js` (21,930 bytes uncompressed), and route-bundle-stats.json shows that chunk
  in the `firstLoadChunkPaths` of 36 routes - /feed, /directory, /collection, every /admin
  page, every authenticated surface. The chunk is shared (it also carries tour-entry code -
  "hoopoe" matches), so DemoBar's own share is a fraction, but its code, its copy, and its
  `markOnboardingSeen` import are demonstrably in there. The project's own recorded principle:
  "parked code should not ride in bundles it is not used by" (progress.md, quoted in
  next.config.ts:287-289).
- **What to do**: in the (main) layout, replace the static import with a lazy one so the chunk
  is only referenced when the demo actually renders it. Cleanest shape:
  `const DemoBar = dynamic(() => import("@/components/demo/demo-bar").then(m => m.DemoBar))`
  at module scope of the layout (a server component may use next/dynamic without `ssr:false`),
  keeping line 153 as is. When IS_DEMO is false the flight payload never references the chunk
  and the browser never downloads it; when true, the demo pays one extra lazy request, which a
  showcase can afford. This would also be only the second `next/dynamic` in the app - the
  bundle lens should fold it into its pattern.
- **Saving**: DemoBar's share of a 22KB chunk off the first load of every authenticated page
  in production - honestly ~2-4KB gzipped plus its parse cost, times every page view.
  0 lines of code.
- **Risk & gate**: low-medium. `npm run check`; `npm run visual` (must be a no-diff run - the
  bar never renders in the baselines); the one thing no local gate covers is the DEMO
  deployment still showing the bar, so the fixer must run `DEMO_MODE=1` locally once and see
  the pill render on /feed before committing. docs/spec/demo.md calls the bar "the one piece
  of chrome the demo adds", so losing it silently would be a real regression.
- **Confidence**: high on the mechanism (string found in shipped chunk, chunk in 36 routes'
  first load); medium on the exact KB attribution because the chunk is shared.
- **Notes**: I checked whether the same argument applies to the demo-seed (~2,150 lines:
  content.ts 964 + people.ts 585 + seed.ts 540 + places.ts 85) riding in the production
  *server* build via `/api/demo/reset`'s static import of `seedDemo`. It does ship - the route
  exists on both deployments by design (the production cron GET answers `{skipped}`) - but the
  cost is server-side function size only, invisible to members. A dynamic
  `await import("@/lib/demo-seed/seed")` after the IS_DEMO check in `runReset` would keep it
  out of the route's cold-start graph for ~2 lines of change; worth doing while touching demo
  code, not worth a finding of its own.

## Owner decisions

- **The email queue exists because Resend's free plan sends 100 messages a day.** The
  1,061-line queue, the 95-message cap, the 20-message reset reserve, the "goes out tomorrow
  at 5:30 am" banner arithmetic - all of it is engineering around that one free-tier number
  (email-queue.ts:32-68 says so in its own header). A paid Resend plan (their first tier)
  removes the daily cap, at which point roughly a third of this file - the budget counting,
  the reserve, `verifySendingAt`, the queued-state banner copy - stops earning its keep,
  though the retry/backoff/lease machinery would still be wanted for provider brownouts. I am
  NOT recommending the spend; the queue works and launch is the wrong week to re-plumb mail.
  But the trade should be written down where the owner can see it: about $20/month versus
  ~350 lines of the most intricate code in the project, plus the launch-day scenario where
  signup number 96 waits a day for a confirmation. Decide after launch, when the real daily
  volume is a number instead of a fear.
- **Nothing else in this territory needs an owner call.** Every subsystem I read is defended
  by a spec, a test, or a dated incident; the findings above are all executable by a later
  session on their own authority.

## Not-findings

(things that look like bloat and are verified intentional - do not re-litigate)

- **email-queue.ts at 1,061 lines is not a queue that a simpler outbox replaces.** The floor
  question, answered: this project has NO cron for mail (both Vercel Hobby cron slots are
  spent - retention.ts header, OPERATIONS.md), so the queue is drained by racing
  opportunistic passes from every page view's `after()` - genuinely multi-producer AND
